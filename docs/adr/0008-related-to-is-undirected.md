# ADR 0008：`RELATED_TO` 是无向的

- 状态：已接受
- 日期：2026-07-16
- 回答了什么：PLAN **从没回答过**「`RELATED_TO` 到底是有向的还是无向的」。这份 ADR 补上那个答案。
- 必须在：M1 声明层开始往图里写关系边之前（写下去之后改要重建全部 `RELATED_TO` 行）

## 决策

**`RELATED_TO` 无向。** 存储时 `(src, dst)` 规范化成 `(min(id), max(id))`，规范化发生在
`EdgeSpec` 的**构造函数**里（`graph/models.py::UNDIRECTED_EDGE_TYPES`）。

读侧 `out_edges_at` 对**且仅对**无向类型放开 `dst = :node`。消费侧取对端用
`Edge.peer_of(node_id)`，不用 `e.dst`。

## 问题：那个没答的问题有一个具身

对称关系（师兄妹 / 夫妻 / 仇敌）作者会自然地**两侧各声明一次**，图层没有任何东西阻止或警告这件事，`store.py` 的契约也没说 `RELATED_TO` 必须单向存。于是：

```python
upsert(c1 → c2, ch10, "师兄妹")   # 作者从萧决这边声明
upsert(c2 → c1, ch10, "师兄妹")   # 作者从顾清音那边又声明一次
upsert(c1 → c2, ch143, "断绝")    # 第 143 章断绝师门：只落了一条
```

`find_conflicts` 只搜 `(src, dst)` 这一个方向，所以它只闭合 `c1→c2` 的旧边。`c2→c1` 的「师兄妹」`[10,∞)` 原封不动地继续有效。

ch150 时 `state_at(萧决)` 说「断绝」、`state_at(顾清音)` 说「师兄妹」——**同一个关系两个互斥的值同时是 CANON**，而 §5.4 的定义是 CANON「可断言为真、可开火」。

**它比 F1/F2 更难堵，因为它不需要任何脏数据**：全程走 `upsert_edge` 的正常路径、每一步都成功、`UpsertResult` 也如实报告了它闭合了什么，没有任何一个环节有机会察觉不对。

讽刺的是它恰好打在 PLAN 自己的 GIF 主角上（§3.1：作者写「师兄」→ 右侧红字「第 143 章两人已断绝师门关系」）——**从顾清音那一侧查，图会说他俩还是师兄妹，红字不会亮。** 将来 R5 若进 v1，它读的就是这条边。

## 论证：为什么是无向

**判它无向的依据是这个仓库自己写的东西。** `edge_type` 那一行的注释是：

```sql
('RELATED_TO',  'single_per_src_dst'),  -- (A,B) 关系阶段单值
```

「(A,B) 单值」的字面意思就是无向。而「**关系阶段**」——看 `test_supersede.py` 里的实际取值：师兄妹 / 断绝师门 / 主仆——本来就是对称的：A 和 B 处在「断绝」阶段，B 和 A 就处在「断绝」阶段。`props.value` 存的是关系**名**，不是**角色**。

### 为什么不选「有向 + `edge_type` 加一列 `symmetric`」

这条路（对 symmetric 类型额外搜一遍反向 `(dst,src)` 的冲突边并一并闭合）通不到一个自洽的地方：

- `symmetric = 1` 恒成立 → `RELATED_TO` 就**是**对称的，那和无向语义相同，却多了一份需要保持一致的行。而且「师父 / 徒弟」这类角色边照样表达不了：声明 `B→A "徒弟"` 会**闭合掉** `A→B "师父"`。
- `symmetric = 0` 恒成立 → 上面那个 bug 原样保留，只是有了一个字段假装它被想过。

`symmetric` 只有在「同一个类型有时对称、有时不对称」时才有意义，而那不是一个边类型该有的样子。

### 为什么不选「自动补一条镜像边」

这是最坏的一种。它就是 §5.4 为了砍掉存储版 `CURRENT` 而**拒绝过的那个东西**：

> 「同名字段存两处就需要一个同步器」

镜像边是第二份真相，需要一个同步器保证它跟着主边走，而那个同步器的 bug 长得和今天这个 bug 一模一样。无向存一份，没有同步器可言。

### 为什么不只在 `find_conflicts` 里加个 `OR`

那会让 `LOCATED_AT` / `KNOWS` / `HAS_STATE` 这些**真正有向**的类型跟着遭殃：`KNOWS` 的 src 是人、dst 是秘密，反向搜是无意义的。规范化把两个方向在**写入之前**就塌缩成同一对，于是 `find_conflicts` 一个字都不用改——这是选规范化而不是选 `OR` 的额外好处。

## 实施的三个要点

1. **规范化在类型层，不在 `upsert_edge` 里调一次。** 调一次就是一条纪律，而漏掉它的产物正是上面那条 bug。放进 `EdgeSpec` 的 after-validator 之后，幂等键 / `find_conflicts` / `insert` 全部自动落在同一个 `(src,dst)` 上，调用方**在物理上造不出**一条没规范化的无向边。

   > **实测的坑：** after-validator `return self.model_copy(update=...)` 在 `__init__` 这条路径上**会被 pydantic 直接丢弃**（只发一条 UserWarning），`EdgeSpec(...).src` 拿到的还是没规范化的值。那正好是这条规范化静默失效的形态，而它唯一的症状是一条警告。所以用 `object.__setattr__`。

2. **读侧必须成对改。** 只做规范化的话，`(min,max)` 是两个 ULID 字典序的抛硬币结果，于是「顾清音和萧决是什么关系」的答案取决于抛硬币——**一半的人物卡上关系栏凭空消失**。这比原来的 bug 更隐蔽。所以 `out_edges_at` 对无向类型放开 `dst`。

3. **`Edge.peer_of(node_id)`。** 存储方向没有语义，消费侧写 `e.dst` 就是错的。

## 诚实说明代价

**角色型关系（「A 是 B 的师父」）在 v1 表达不了。**

v1 没有这个消费者：R5 读的是关系阶段，局部图渲染的是边上的标签。真要它时的正确做法是按 ADR 0005 的增长规则**加一个新的有向边类型**（那时才会有一个真实的查询要它），而不是把 `RELATED_TO` 掰成有向——后者会让全部已有的关系阶段边失去它们的语义。

## 若此决策错误，修复成本是什么

**不对称，这就是本 ADR 要在 M1 之前定的理由：**

- 现在改：**零成本**（库里还没有 `RELATED_TO` 行）
- M1 之后改：要重建全部 `RELATED_TO` 行，且**没有信息可以恢复方向**——规范化把作者原本写的 `(src, dst)` 顺序丢掉了。想反悔成有向的话，那个顺序得从 `decision_log` 的引语里重放（这正是 §5.7 那张表存在的理由，也是它第一次真的派上用场的地方）。
