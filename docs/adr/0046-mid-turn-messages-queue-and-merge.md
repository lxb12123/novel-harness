# ADR 0046：一轮跑着的时候还能说 —— 排队，在步的边界并入，不打断

- **状态**：已接受（2026-09-12，作者提出）
- **推翻了**：不是原始需求文档，是 `api/chat.py::_Running` 那条**对作者可见的**行为：
  一轮跑着的时候再发一句 = 409「这段对话正在跑上一轮」，输入框灰着。
  **闸本身一个字没动**（同一段对话同时仍然只有一轮），变的是「第二句话去哪儿」。

## 一句话

作者的原话：**「像 codex 那样，新的消息可以直接发出去，模型可以读，并且不会耽误正在做的。」**

答案：**不是并发，是排队 + 在步的边界并入。**

---

## 机制

一轮是「模型调用 → 派发工具 → 再调用」的**串行**循环（`agent/loop.py::run_turn`）。
中途那句话：

1. `POST …/chats/{id}/say` 把它放进正在跑的那一轮的**信箱**（`Mailbox`，进程内，
   和 `Cancellation` 一起挂在 `_Running` 那张表上）。**这条路由不等、不打断、不落库。**
2. loop 只在两个地方看信箱：
   - **每一次模型调用之前**：取出来，按正常的作者消息 `with_author()` 追加进 canonical、
     落库、喊一声 `author_said`。于是模型下一步就读到了，正在跑的那一步（一次模型调用、
     一批工具、一稿正文）一个字都不受影响。
   - **模型「说完了」的那一刻**：信箱里有话就接着跑，没话才收场。「说完了」是对上一句
     而言的；作者已经又说了一句，DONE 不成立。
3. **一句都不丢**：收场（按停 / 到闸 / 出错）时信箱里剩的也并进对话、落库；那几句没被
   回答，`TurnReceipt.unanswered` 数出来，界面说一句「它没来得及看，再说一句它就会读到」。
   下一轮靠的是 ADR 0019 既有的 resume：尾巴上是作者的话，模型接着答。

## 为什么不是并发

- **对话的写入只有 loop 那一条线。** 两条线各写一次就撞乐观并发闸
  （`_TurnRun.__init__` 那段实测故障：先按的被判失败，后按的反而通过）。信箱让第二句话
  也从 loop 那条线写进去。
- **模型一次只能读一份上下文。** 「不耽误正在做的」和「它能读到」在同一时刻不可能
  都成立——一次模型调用发出去就发出去了。能做到的是**最早的下一个边界**，那正是
  Codex / Claude Code 的做法（排队，下一步注入）。
- **步数 / 额度那几道闸照旧管着。** 接着跑不是无限跑：`steps < max_steps` 在循环头上，
  信箱不给它开后门。

## 界面

- **「停」挪到发送那颗圆钮上**（作者同日点名）：跑着、框里没字 = 停；框里有字 = 发送
  （跑着时发的是插话）。跑动条上原来那颗「停」撤了——同一个动作只有一个入口。
- 输入框跑着的时候**不再灰**（灰的只剩「跑着的是另一段对话」那一档）。
- 中途那句先淡一档「排着队」+ 后端那句回执（「记下了，它下一步就会看到。」）；
  `author_said` 到手就变成正常的作者气泡，站在模型真的读到它的位置
  （`chat.ts::ProgressLine.author`）。
- `queued=false`（那一刻刚跑完 / 在跑的是另一轮）：那句话还回输入框，后端那句话原样说，
  作者再按一次就是正常的新一轮。**不静默转成新一轮**——`turn.isPending` 收尾那几十毫秒
  里发新一轮会撞 409，而一个转着圈又什么都没发生的按钮比一句话更糟。

## 错了修复成本

- 机制全在两处：`agent/loop.py`（`Mailbox` + `take_mail`，不传信箱逐字节不变，
  `tests/test_agent_loop.py` 最后一节钉着）和 `api/chat.py::say_mid_turn`。
  拆掉 = 删这两处 + 把「停」放回跑动条。canonical 里已经落的那些作者消息是正常的
  作者消息，不需要迁移。
- 已知限制：**中途那句在信箱里、进程死了就丢**（`_Running` 本来就是进程内的，
  同「停」）。界面上它还淡着没变实，作者看得见它没进去；`onSettled` 会把没变实的还回
  输入框。
