# ADR 0020：干净的抽取结果自动生效，退路是「可查 + 可改」而不是事前批准

- **状态**：已接受
- **日期**：2026-08-10
- **推翻了**：不是原始需求文档，是**本仓库自己**——
  [ARCHITECTURE.md §10 约束 3](../ARCHITECTURE.md#10-不可违反的约束) 的后半句
  「**Agent 不得污染 Canon**」。前半句（`PROVISIONAL` 永不开火、永不断言为真）**原样保留**。
- **相关**：[ADR 0004](0004-declaration-over-extraction.md)（声明优于抽取）、
  [ADR 0005](0005-set-judgment-only.md)（只做集合判断）、
  [ADR 0018](0018-cast-is-derived-not-declared.md)（在场从正文推）、
  [ADR 0019](0019-agent-loop-not-graph.md)（模式二）
- **决策日志**：`docs_dev/2026-08-12-模式二与事后可查可改的收尾快照.md`（它替掉了 08-10 那块板子；旧板子在 `git show f10ddbb:docs_dev/2026-08-10-模式二与事后可查可改的进度板.md`）（记「当时怎么想」，非权威）

## 决策

**一条例外 bucket 都没进的抽取结果，自动从 `PROVISIONAL` 升到 `CANON`，作者不点。**
升的时候写一条 `decision_log`，`actor='system'`。

三个例外 bucket **照旧进队列，一条都不自动升**：

| bucket | 触发条件 |
|---|---|
| `edge_conflict` | 抽出来的状态与当前 Canon 冲突 |
| `low_confidence_main` | 主要人物相关，置信度 < 0.70 |
| `new_character` | 抽取发现尚未登记的人物 |

实现在 `extract/auto_canon.py::promote_clean_facts`，复用既有的
`confirm_provisional_{events,edges}`——**不另开第二条升 CANON 的路径**。

## 为什么推翻约束 3 的后半句

### 1. 「不烦你」和「不用你」今天是同一件事

约束 3 立的时候，前提是「作者会来清队列」。真实情况是：**升 CANON 只有两条路，
两条都要作者亲手点**（`review_proposal(ACCEPT/EDIT)` 和 `confirm_provisional_*`）。
于是高置信度的抽取结果**既不打扰作者、也永远用不上**——

> 不烦你 = 也不用你 = 白抽（模型的钱已经花了）。

作者库里的实测：`extraction_run` 0 行、CANON 事件 0 条、pending 提案 0 条。
**不是队列积压，是这条路从来没人走过。** 一个从来没人走的确认环节保护不了任何东西。

### 2. 约束 3 保护的东西，换一种方式保护得更好

约束 3 真正怕的是「图里出现作者没同意过、且他发现不了、发现了也改不掉的东西」。
**三个词，事前批准只解决第一个。**

2026-08-10 的换法是：

| 怕什么 | 事前批准 | 本 ADR |
|---|---|---|
| 作者没同意 | 挡住 | **不挡**（承认这是代价） |
| 发现不了 | 挡住 | 每一步留痕（`extraction_run` / `model_call` / `decision_log`），日志页可查 |
| 改不掉 | 挡住 | `corrections.py` + `/canon/...` 三条路由，能改 knowers / participants / KNOWS↔BELIEVES |

**顺序是硬的：编辑能力（1.1）先于自动生效（1.2）落地，不是同时。**
反过来的话，中间会有一段时间是「系统自动改你的书，而你改不回来」——
那才是真正不可接受的状态。

### 3. 前半句为什么保留

`PROVISIONAL` **仍然永不开火、永不断言为真**。本 ADR 改的是「怎么离开 PROVISIONAL」，
不是「PROVISIONAL 能不能被当真」。没升上去的事实照旧不进上下文、不进规则、不进 prompt。

### 4. 失败方向是 fail-safe

自动升失败 ⇒ 事实**留在 `PROVISIONAL`** ⇒ 不进任何上下文。
**不许因为升不上去把整个抽取 run 标 FAILED**：正文已经抽完了，那次模型钱已经付过。

## 代价（承认，不粉饰）

- **`knowers` 是推断不是文本事实**，自动生效之后它是最可能出错的一维——
  而认知边界正是这个产品唯一的独家价值（ARCHITECTURE §1）。**退路是编辑 + 可查，不是事前批准。**
- **作者可能一直不看日志。** 那时错误会静默累积。这是本 ADR 最大的赌注：
  赌「错了能改」比「错了先拦住」更符合一个每天写 5000 字的人的实际工作方式。
- **`decision_log` 会长得快得多**（每章都有 system 行）。它是 append-only 且不可重建的资产，
  体积增长是有意接受的——日志页要能按 `actor` 过滤，否则作者自己点过的 30 次确认
  会被淹没在几千条 system 行里。

## 什么条件下推翻本 ADR

满足**任意一条**就退回事前批准（或改成分级批准）：

- **真书上实测：自动升进 CANON 的事实里，作者事后改掉的比例超过某个阈值。**
  阈值今天定不了——**没有真书数据之前不许在这儿编一个数字**（同 EVAL_PROTOCOL 的规矩）。
  日志页（2.2）落地后这个比例才第一次可测。
- **出现「作者改不回来」的形态**：某一维事实自动写进去了，而 `corrections.py` 没有对应入口。
  那时先补编辑入口，补不了才退回批准。

## 若此决策错误，修复成本是什么

**中等，且不对称：**

- **关掉自动升**：一个开关。已经升上去的 CANON 事实不会因此回滚——
  它们已经参与过起草，回滚会让历史上下文对不上。
- **已经错了的事实**：靠 `corrections.py` 一条条改。**这就是为什么 1.1 必须先落地**——
  没有它，本 ADR 的修复成本是「无穷大」而不是「中等」。
- **日志膨胀**：可以归档，但 `decision_log` 三个触发器禁 UPDATE/DELETE，
  归档只能是「另建一张表 + 只读旧表」，不能删。这条代价是永久的。

## 补记（2026-08-25）：`new_character` 那一档**从表里拿掉了** —— 认不出就建，不要问

维护者裁定。**上面的决策正文一字未动**，改的是那张表少了一行：

| bucket | 触发条件 | 今天 |
|---|---|---|
| `edge_conflict` | 抽出来的状态与当前 Canon 冲突 | **照旧** |
| `low_confidence_main` | 主要人物相关，置信度 < 0.70 | **照旧** |
| ~~`new_character`~~ | ~~抽取发现尚未登记的人物~~ | **删。认不出的人物直接建成 Character** |

实现是 `extract/service.py::_create_unknown_characters`，跑在解析事件**之前**。

### 那条规矩的顾虑是真的

原表把 `new_character` 列进例外，怕的是**模型往花名册里塞垃圾**：一个错建的「人物」
会被 R2/R3 拿去匹配正文 → 误报 → 作者关掉整个功能（ADR 0005 的生死线）。
这个顾虑今天仍然成立，见下面「它会认错」。

### 但它假设了「花名册里本来有东西」

在一本**空花名册**的书上，那条规矩的实际效果是：

```
花名册空 → 事件里的人认不出 → 整条事件丢（`if not participants`）
        → 花名册还是空 → 下一章接着全丢
```

唯一出口是作者去清 `new_character` 提案。真书实测（`book.db`，158 章）：
三章抽取，模型抽出 35 件事，**引擎一件没留**；22 个提案从 2026-08-15 PENDING
到 2026-08-25，**一条都没被确认过**。

> **它不是「慢」，是「不工作，而且没人告诉作者」。** 三次 run 全是 `SUCCEEDED` +
> `errors_json='[]'`（那个哑告警 2026-08-24 已补，见 `extraction_yielded_nothing`）。

### 它和 ADR 0018 在同一个仓库里同时成立不了

[ADR 0018](0018-cast-is-derived-not-declared.md) 的整条论证是**「在场是从正文推出来的，
不是作者填的表单」**，理由第一条逐字写着：

> 没名字的配角（「那个卖伞的老头」）**永远进不了花名册**，作者填不出来。

而 `new_character` 提案要求的恰恰是**作者去把那些名字一个个填进花名册**。
两条规矩管的是同一批人，方向相反。这次裁定选了 ADR 0018 那一侧。

### 不拿 `usable_for_rules` 当「未确认」的替身

建出来的人物和作者亲手建的**一模一样**。拿 `usable_for_rules=False` 标记「这个是机器
猜的」，等于在 ADR 0004 定死的一个语义（「这个称呼能不能拿去匹配正文」）上加载第二种
意思，而下一个人只会读到第一种。

### ⚠️ 它会认错，而认错的代价必须有出口

真书那 22 个名字里「**袭人**」是真会误命中的：这本书里满篇「寒气袭人」「香气袭人」。

- **今天它伤不到规则**：R3 只看对白标签位；R2 要 `first_appears_chapter`，而那个字段
  没有浏览器入口。
- **它伤的是「这一章提到了谁」和喂给模型的上下文**：袭人的档案会被塞进一场她不在的戏，
  花名册的出场频率也会被它灌水。

**所以「花名册可删、可改名」是这条裁定的配套，不是可选项**，两者同一批改动落地：
自动建 + 不能删 = 单向阀，模型认错一个，那个错永远留在库里往上下文里塞噪声。

### 一条边界，别越

    抽取那一侧   本来就是模型判断        ← 改成信它，没问题
    规则那一侧   R2/R3 必须是字符串匹配   ← **不许改**，撞 ADR 0005

「这一章提到了谁」今天是给面板和上下文用的，**不是给规则用的**，所以它改成信模型
不撞铁律。ADR 0005 当年测算过：语义规则 5~20 条误报/章，作者会关掉功能。

### 三样**没有**跟着改

- **歧义（`ambiguous`）照旧整条拒收。** 「师兄」同时指向两个**已经存在**的人时，
  建第三个只会让歧义更重——ADR 0004：产品从不替作者挑。
- **模型自己说是别名的 surface 一个都不建。** `analysis.aliases` 里的每一条都是
  「这是某个已有人物的另一种叫法」；不够格落成别名 ≠ 这是个新人，
  把它建成人物就是让同一个王熙凤在花名册里有两个身子。
- **已知人物的档案照旧只读**，直到作者显式审阅。新建的那个人才带上这一次的画像。

### 历史提案怎么办（**没做，明说**）

真书里那 22 条 `new_character` 提案还是 PENDING，而浏览器里那一支不再渲染。
后端的审阅链路（validation / audit / apply / `bystander` 动作）**原样留着**——
它们是历史行的处理路径，同 `decision_log` 那批废弃 kind 的道理。
**但没有人给那 22 条一个了结**：它们指的那些人下一次抽取会被自动建出来，提案本身
成了无主的。要不要批量 `reject` 掉、要不要在界面上给它们一个「都不用管了」的收口，
**是维护者的裁定，这一批没做。**
