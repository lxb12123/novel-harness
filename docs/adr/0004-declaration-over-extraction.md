# ADR 0004：声明优于抽取

- 状态：已接受
- 日期：2026-07-16
- 推翻了什么：需求文档第 22 节第 2 项（初始图谱抽取与作者校对）、第 17 节 Import 页、第 7 节把 `Foreshadow` / `Secret` / `KnowledgeItem` 列为抽取产物
- 这是整个计划最重要的单点改动

## 决策

**认知边界、秘密、伏笔由作者声明，不由系统抽取。**

导入 = 章节切分 + **别名角色册**自动抽取 + 作者做**聚类确认**（不是逐条确认）。

增量抽取（M4）只用于 PROVISIONAL 层，永不直接进 Canon。

## 论证

### (a) 130 小时墙

原设计：300 章存量小说 ≈ **16,500 条待确认 Proposal** ≈ **130 小时**（16 个工作日）≈ 把整本书重读一遍的 3.5–5 倍。

作者要花 130 小时把**自己本来就知道的事**教给电脑，然后才能开始写第 301 章。

**没有任何个人作者会走完这个流程。** 他们会在第 200 条 Proposal（大约第 1 小时）弃用。

### (b) 而且那 130 小时的产出物是错的

| 任务 | 实测水平 |
|---|---|
| 中文网文 NER（PER/LOC/ORG）SOTA | F1 **73.74** |
| ChatGPT 零样本中文网文 NER | F1 **21.90** |
| GPT-4 抽叙事文本人物关系 | F1 **0.276** |

> 来源：GenWebNovel / Conan 数据集。**这些数字动工前应复核**——它们是本 ADR 的定量依据。

关系层一多半是错的。而认知边界建立在关系层之上，误差还要叠加。

### (c) 范畴错误：秘密和伏笔不是「事实」，是「作者的意图」

**墙上挂了一把枪，它是不是伏笔，取决于作者第 200 章打不打算开枪。**

**这个信息物理上不存在于已写文本中。** 任何抽取器都是在猜。

文档把 `Foreshadow` / `Secret` 列为必须自动抽取项，是一个范畴错误。

反过来说：作者手填「第 47 章埋了 X，计划第 200 章回收」+ 到期提醒 = **20 行代码、零抽取风险、90% 的价值**。

## 声明成本：为什么这次是 1 小时不是 130 小时

| 对象 | 量级 | 来源 | 成本 |
|---|---|---|---|
| `Secret` 节点 | **5–50 个/本** | 作者声明 | 20 分钟 |
| `KNOWS(角色, 秘密, since_chapter, evidence)` | 每秘密 2–8 个持有者 | 作者声明 | 10 分钟 |
| `BELIEVES(角色, 秘密, believed_value)` | 0–5 个/本 | 作者声明 | 5 分钟 |
| 别名角色册 | 50–200 个实体 | **自动抽 + 作者聚类确认** | 30 分钟 |
| 场景 `cast` | 每场景 2–5 人 | mention 自动建议 + 点确认 | 5 秒/场景 |

**一本 200 万字的小说，全部前置声明成本 ≈ 1 小时。对比 130 小时。这个差距不是优化，是生死线。**

## 为什么角色册是唯一值得前置人力的东西

- 量小（300 章的书约 50–200 个实体）
- 作者几秒就能判
- **所有下游都以它为键**
- GenWebNovel 显示 **PER 恰好是抽得最准的一类**，错误集中在别名归并——**正好是人工最省力的地方**

**确认形态必须是对聚类的**：「李明在 47 章里被叫作明哥 —— 全部接受？」= **1 次点击换 47 条**。不是对条目的。

**扁平 Proposal 队列永不做**——它是错误心智模型的 UI 化身。

## 别名不做实体消解（这跟 GraphRAG 是反的，且是故意的）

GraphRAG 按名字做实体消解，会把「顾姑娘 / 清音 / 魔尊」合并掉。

**而这些别名差异恰恰编码了关系阶段和认知边界**（化名 = 别人不知道他是谁 = 认知图的边）。**它们是 canon，不是噪声。GraphRAG 的 entity resolution 会正好摧毁这个项目最有价值的信号。**

别名表的诚实约束：
- 一个 surface 映射到 > 1 个 node_id 时（「师兄」）→ 标 `ambiguous`，**规则不使用**
- **2 字以下别名 UI 层直接拒绝录入**（「音」「决」是灾难）

## 副作用：这一改，面板变成零误报

面板由**作者声明的 `cast`** 驱动，去图里做一次集合查询。它**不读正文**：

- 零 LLM
- 零 NLP
- **零误报——因为它对文本不做任何断言**

它只是在告诉作者：**你自己在第 88 章告诉过它的事。**

推论（对 demo 质量很重要）：**合成 demo 书的面板质量 = 真书的面板质量**，因为两者都由声明驱动。「demo 0 误报 / 真书 5 条/章」这个预期落差在 v1 不存在。它只存在于 M4 的增量抽取，那里 demo 展示真实抽取质量。

## 若此决策错误，修复成本是什么

**几乎为零，因为这是加法不是减法。** 如果将来抽取质量足够（比如 F1 > 0.8），把抽取结果灌进 PROVISIONAL 层、走 exception-driven 确认即可——声明层原样保留，作者可以少声明。

反向不成立：先做全书抽取，作者在第 1 小时弃用，没有第二次机会。
