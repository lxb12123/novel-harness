# ADR 0013：起草长度是「作者随请求给」的参数，不是后端存的设置

- 状态：已接受
- 日期：2026-08-02
- 解决的问题：作者要自己定「每章/每场写多少字」，产品层怎么落
  （ADR 0011 D1 只定了双语单位、默认档与硬上限，没定**选择权归谁、存在哪**）。

## 决策

**长度是起草请求的一部分**：前端把作者选好的 `LengthSpec`（语言 / 下限 / 目标 / 上限）
随 `/draft` 请求发给后端，后端只做硬上限校验，然后整条生成链（长度指令、续写档）用它。

```text
作者在「起草长度」控件里选（默认 2,000–2,500–3,000 字，可改）
   ↓ 存本机（localStorage，换书不丢——作者的偏好一般全书一致）
   ↓ 随 /draft 请求发给后端
   ↓ LengthPolicy.validate_spec（不可协商硬上限：中文 20,000 / 英文 12,000）
   ↓ generate_draft 用这份 spec：长度指令 + under-min 续写一次（续写指令嵌入该档）
```

## 为什么

- **作者是唯一知道这场该写多长的人**：2,000–3,000 只是默认档，不是产品限制。
- **不落后端**：长度不是书的数据，是「这一次请求想写多少」的意愿；落库反而要
  维护同步（书换了、设备换了、心情换了），而它随时可重发。
- **硬上限必须后端再验一遍**：前端校验可以被绕过，`validate_spec` 是那条不可协商的
  边界（ADR 0011 的 hard maximum 落到 HTTP 层）。
- **M2 实验档不受影响**：kill-gate 的 225 格继续用冻结的 `M2_LENGTH_SPEC`，
  不读作者设置、不读环境变量（ADR 0011 D1 原话，改实验档 = 改卷子）。

## 分界线（什么已就绪 / 什么等开闸）

已就绪：前端 `DraftLengthControls`（本机存储 + 校验）、后端 `LengthPolicy.validate_spec`、
`/draft` 请求体的 `_DraftLengthBody` 形状、`continuation_instruction(length, cumulative)`。
等 M2 PASS：`/draft` 从 501 换真实现时，把请求里的 `LengthSpec` 一路传进
`assemble()` + `generate_draft()`（路径不动，只是接线）。

## 若决策错误，修复成本

低。长度本来就在请求体里，改成「后端按书存」只是加一张表 + 一个查询，
已发出的请求不受影响；作者自定义档与实验档的隔离已经由 `M2_LENGTH_SPEC` 常量保证。
