# ADR 0036：调度只分名额，不决定做不做 —— 「报了什么」必须等于「做了什么」

- **状态**：已接受
- **日期**：2026-08-23
- **推翻了**：不是原始需求文档，是**本仓库自己**——`summary_schedule.py` 把一个排队用的
  分数当成了准入门槛；`chapter_refresh.py` 把「没有总结」和「总结是旧的」塞进同一份
  「缺哪几样」的清单；`ChapterRefreshCoordinator.run` 根本不看那份清单。
- **相关**：[ADR 0029](0029-save-triggers-snapshot-refresh.md)（保存触发快照刷新——本 ADR 修的
  是它下游那三层）、[ADR 0030](0030-versioned-summaries-and-advisory-reconciliation.md)
  （版本化总结；「新正文的机器总结可以正常替换它」那句话是本 ADR 自动覆写那一条的依据）、
  [ADR 0035](0035-autopilot-cut.md)（「撤回过的章不许被自动买回来」——那条纪律在本 ADR 里
  第二次被钉住，这次是在扫描那条路上）

## 决策

**一个数只回答一个问题。** 三层各改一处，合起来是同一条主张：

| 层 | 从前 | 现在 |
|---|---|---|
| 排队 | 权重既排序**又准入**：算到 0 的章不进候选池 | **权重只分配一轮的名额**，要干活的章全部进池子；唯一豁免是作者当前打开的那一章（防抖，与远近无关） |
| 下单 | 「缺不缺」一份清单捎带三件事，表达不了「旧不旧」 | 两个独立判据收敛到 `chapter_refresh.summary_alignment` **一个出口**：`paired / missing / stale / retracted` |
| 执行 | 协调器不读 `missing_branch_mask`，`summary_state == PENDING` 就跑 | **按 mask 决定跑哪几支**；没排的支落终态（不留 `PENDING`） |

外加两条随之成立的：

- **覆写单真去重买一份、自动覆盖**（不是「只提示」）。
- 保存事务算出的那份「失去依据」清单**接住并落库**（`chapter_refresh_run` 那三列 JSON）。

## 为什么

**三处都是同一个病：一个数在两个地方各有一份含义，而没有任何测试站在缝上。**

### 证据（2026-08-22 实跑，不是推测）

**权重当门槛。** 原点不是固定的，是作者当前打开的那一章。所以他跳回去看第 2 章的那一刻：

```
第 1 章    权重 1.0
第 3 / 5 / 20 / 100 / 158 章    权重全部 0.000
```

一本 158 章的书，**156 章瞬间「不存在」**——那些章缺总结也永远不会被补。而调度模块自己的
文档只说权重用来「排序处理」和「省预算」，**从没有「权重 0 就不调度」这一条**。
（顺带：文档写的归零点是 50，代码是 60，两边对不上。）

**报了覆写、实际没排。** 造一章「正文已改成新版、总结还挂在旧快照上」：

```
扫描器      state=stale, needs_work=True   →  返回 "queued_overwrite"
实际下的单  验证 + 抽取                     ←  总结那一项不在
```

扫描器**判对了**，它问的是「这份总结当初照着哪一版正文写的」。但真正下单那一步问的是另一个
问题——「这一章**有没有**总结？」有啊，那份旧的还挂着。于是回答「不缺」，一单都不下。

**排了什么和跑了什么对不上。**

```
ensure_refresh_coverage(skip_summary=True)  →  mask = 0b101（总结位已剥掉）
pump_once 之后                               →  总结 adapter 仍然真调了 1 次模型
```

也就是说**焦点防抖在执行层根本不生效**。这一条最贵：它是「自动覆写」那条决定的成本论证
所依赖的前提（「作者改了一下午、存了 30 次，一次都不买」），而它当时只写在记录里。

### 为什么这个病特别容易犯

**因为两边各自看都是对的。** 权重用来排序是对的，用来省预算也是对的；
「有没有总结」这个问题本身也没问错。**没有任何一边是错的，错的是它们不知道对方存在。**

而代码审查看的是一个文件、一次改动，天然看不见缝。**只有测试能站在缝上。**

## 定期扫描是主路，保存不是必需

**这一条是产品要求，不许弱化成「保存触发 + 扫描兜底」。** 保存根本不是唯一的正文变更来源：

- 作者在别的软件里改稿（README 里那位用 WPS 的人），压根不经过工作台；
- 导入一本已经写好的书，一次保存都没发生过；
- 保存失败、进程崩了。

只要「覆写」依赖保存，上面每一种都会漏。**扫描必须自给自足，不能指望有人来通知它。**
保存时顺手标一下是可选的加速，标不标都不影响正确性。

## 自动覆写为什么不是「只提示」

担心的是「改个错别字就重新买一次」。**防抖挡住了它**——但前提是防抖真的生效，
所以本 ADR 的顺序是硬的：**先让协调器认 mask，再开自动覆写。**

```
作者正在改第 20 章        → 这一章不排总结（焦点防抖）
他改了一下午、存了 30 次  → 一次都不买
切走 / 焦点心跳过期       → 才够格
生成总结                  → 幂等（判据是 prompt_hash，内容地址）
```

**所以不是「每保存一次买一次」，是「每离开一次改动过的章买一次」。** 那个频率是合理的。

而且 ADR 0030 本来就写着「以后正文产生新 generation 时……**新正文的机器总结可以正常替换
它**」——**自动覆写才是设计里的行为**，「只提示不重买」反而是偏离。

## 留下的守卫（每一处都做过反向验证）

不留的话，过几个月同一处会长出第二个数。

| 守卫 | 它坏掉时代表 |
|---|---|
| `test_distance_never_removes_a_chapter_from_the_candidate_pool` | 阀门被装回去了 |
| `test_reporting_an_overwrite_means_the_order_carries_the_summary_branch` | 判据又退回「只问缺不缺」 |
| `test_a_round_never_claims_more_than_the_order_carries` | 下单层漏了分支，而调度器仍在撒谎 |
| `test_a_retracted_summary_is_not_a_gap_for_the_scanner` | 作者删一次、系统买回来一次（ADR 0035 那条纪律，这次在扫描那条路上） |
| `test_the_coordinator_runs_exactly_the_branches_the_order_carries` | 执行层又不看 mask |
| `test_a_long_afternoon_of_saves_buys_nothing_and_leaving_buys_exactly_one` | 防抖又只存在于记录里——**它数的是模型调用次数，不是状态列** |
| `test_the_save_transaction_hands_back_the_facts_that_lost_their_support` | 那份清单又被扔了 |
| `test_the_list_reaches_the_run_row_instead_of_dying_in_the_receipt` | 清单算出来了但没走到库里 |

最后两条是同一件事的两半。那份账**确定性、纯查库、不花一分钱**，答的是改老章最容易出事的
那一问——「你刚删的那句话，是后面某些设定的唯一出处」。它从前只喂了一次 canon bump 就被
丢在 `commit_chapter_snapshot` 里。

## 范围之外

- **不动注入侧**（拼 prompt 时怎么选总结）——那一侧用的是字数预算，不是权重，实现是对的。
- **`sync` / 外部改稿那条路上的同一份账仍未接**（`importer._read_one_chapter` 那一行照旧
  丢返回值）。落点已经定了（就是 `chapter_refresh_run` 那三列），但它不经过 `_trigger_refresh`，
  要另找入口。**这是本 ADR 已知没做完的一半，而且它正是 WPS 那位作者走的路。**
- `book_summary_status` 仍把撤回显示成「没有总结」（作者要看得见自己撤了）——
  那是读端，和「系统该不该自己掏钱补一份」是两个问题，**别修成一致**。

## 若决策错误，修复成本

**低。** 三处都是判据改动，没有数据迁移。

真要往回退，先回答一个问题：**退回去之后，「报了什么」和「做了什么」由谁来对？**
今天的答案是那八条守卫。**没有第二个答案时，别退。**
