# ADR 0026：能力表只装「学不会的」——协议保证的删掉，公开的外包，测不起的才留

- **状态**：已接受
- **日期**：2026-08-13
- **推翻了**：不是原始需求文档，是**本仓库自己**——
  [ADR 0025](0025-unregistered-routes-ask-the-endpoint.md) 落地一天后就发现它解决错了问题，
  以及一条从没写下来过的隐含前提：**「路由的每一位能力都该由一张表来答」**。
- **相关**：[ADR 0024](0024-a-turn-is-a-conversation-not-a-black-box.md)（边跑边发事件 ——
  **它是本 ADR 的受害者，也是最大的受益者**）、
  [ADR 0025](0025-unregistered-routes-ask-the-endpoint.md)（去问端点自己；**收益被本 ADR 缩掉大半**）
- **决策日志**：没有。当天的实测证据写在下面「实测证据」一节。

## 决策

**判据只有一句：这一位能不能靠别的办法拿到？能拿到的就不进表。**

| 字段 | 处置 | 靠什么拿到 |
|---|---|---|
| `supports_streaming` | **删掉** | **协议保证**：`stream` 是 OpenAI Chat Completions 的基本功能，不是可选扩展 |
| `supports_stream_usage` | **删掉** | 无条件要；端点不认就忽略，读取侧本来就落 `None` |
| `max_context_tokens` | **外包** | 一份打包进来的公共快照（`draft/windows.py`），可一键更新 |
| 单价 | **新增，同一份快照** | 同上 |
| `max_output_tokens` | **留在表里** | 公共表这一列实测滞后一整代，只能自己查证 |
| `reasoning_dialect` / `max_tokens_field` | **留在表里** | 四家四种写法，发错 = 400 或**静默不生效**（钱照花） |
| `reserve_ratio_high` | **留在表里** | 只能实跑长稿测右尾 |

**学得会的东西（一次失败就知道）由运输层学，不进表**：
`provider._NO_STREAM`（这家真不吃流式）、`provider._NO_STREAM_OPTIONS`（不认那个字段）。
两者都是进程内、不落盘、**且降级必须一路走到屏幕上**（`CompletionResult.fell_back_to_one_shot`）。

## 为什么

### 1. 原来那个默认方向是错的，而它的代价不是「保守」

`supports_streaming` 的旧规矩是「没登记就不敢流式」。听起来是 fail-closed 的美德，实际是：

> **作者接任何自定义端点，「停」按钮和「边写边看」一起哑掉，而且不报错。**

两个模块各自都对（`plan_call` 谨慎、ADR 0024 复用同一条流），**接缝处静默失效**。
更糟的是它有历史：那个降级是 2026-08-12 上午**有意选的**，理由写得清清楚楚——
「起草整个不能用」和「停不下来但写得出稿」之间选后者。当天晚上 ADR 0024 落地，
**降级的代价从「一个还没做出来的按钮不灵」涨成「屏幕上一动不动」**，
而做那个选择的注释一个字没变，也没有任何东西会提醒谁回去重算这笔账。

### 2. 对照过别人怎么做（2026-08-13 查证）

- **Cursor**：custom OpenAI-compatible 模型有个 **Verify** 按钮，点一下发**一次流式请求**。
  它**根本不存 `supports_streaming` 这一位**。不在它精选表上的模型是**砍功能**
  （Agent / Edit 直接不给用，subagent 里静默忽略），比我们的降级还狠。
- **Aider**：直接用 `BerriAI/litellm` 的 `model_prices_and_context_window.json`，
  模型缺了就去给那个 JSON 提 PR。**那是这个生态事实上的共享真相源。**
- **Cline / Roo Code**：自定义端点靠**用户自己在设置里填**窗口
  （而 Cline 有个已知 bug：填了不生效，Issue #2073 —— 和我们「表里有数没接线」同一种病）。

**结论不是「表是过度设计」**：Cursor 也有表，降级还更狠。错的是**往表里塞了协议已经保证的东西**。

### 3. 手抄一张表没有终点

2026-08-13 上午照官方文档把 Anthropic 从 1 条抄到 13 条，用了半天。同一天下午发现：

- OpenAI 那四条**本来就是全的**（白查）；
- DeepSeek **查不了**（官方文档站在维护者机器上 TLS 全断）；
- 抄进去的 13 条**下个季度就旧**。

而那份公共表 3,003 个模型、社区持续提 PR，实测**我们表里九条它全中，数字一致**。

## 实测证据（2026-08-13）

**一、公共表在两维上的可信度截然不同**——这条决定了只裁哪一列：

```
deepseek-v4-flash     窗口：1,000,000 ✅ 与官方一致
                      输出上限：8,192 ❌ 官方 384,000（差 47 倍，是上一代的值）
```

所以**只裁窗口和单价**，输出上限永远归本仓自己查证过的表。单价那一列不同：
**它是 litellm 的主业**，被维护得最勤。

**二、缓存那段必须单独计价**（`estimate_cost`），否则这个项目的账系统性偏高：

```
一次典型起草（输入 8,000 / 命中 7,800 / 输出 3,500）
  命中缓存    $0.001744
  不命中      $0.003710      ← 命中省 53%
```

一本 723 章的书前缀几乎不变，命中率能到 98%。按原价算能高一个数量级——
而这个产品的成本故事整个押在前缀缓存上。

**三、`stream_options` 无条件发是安全的，但不能真的「无条件」**：
它一旦出现在 `nh gate` 的 wire 上就是**改卷子**（EVAL_PROTOCOL §2）。
判据因此收窄成「这一次要不要可中断」——那恰好是「产品起草」和「M2 三臂」的分界线，
后者永不设它。`test_gate_route_is_untouched_…` 实测 gate 的 wire 一个字节没变。

## 代价（承认，不粉饰）

- **默认乐观了。** 真不支持流式的端点会赔一次失败的调用，然后才被记住。
  上限是每条路由一次（进程内），而换端点本来就要重启。
- **公共表的窗口可能是错的**，尤其对自建部署。那道闸是**主机名必须认识**
  （`_HOST_PROVIDERS`）——`localhost` 上一个随手起名叫 `deepseek-chat` 的量化小模型
  **一个键都不查**。⚠️ **这条第一版写漏了**（先查裸名、主机只用来补前缀），
  被 `test_a_lookalike_host_is_not_believed_either` 当场抓住。
- **钱是标价估算，不是账单。** 作者可能有折扣、走中转、用免费额度。屏幕上必须带「约」字。
- **ADR 0025 的收益缩掉大半。** 它原来的卖点是「让自选端点也能流式、也有账」，
  这两样现在协议和运输层就给了。它只剩「按上游逐条取下确界的窗口」——
  仍然比公共表更准（实测 384,000 vs 1,000,000，方向是更保守），但小得多。
  **写在这儿是因为一个模块的价值缩水了却没人回来改说明，正是本仓最常见的骗人文档。**

## 什么条件下推翻本 ADR

- **出现一批真不支持流式的端点**，作者反复赔那一次失败的调用 ⇒ 把
  `_NO_STREAM` 落盘，或者给设置页加一个「这个端点不支持流式」的勾。
- **公共表被证明不可信**（窗口填错导致请求被拒）⇒ 把 `_HOST_PROVIDERS` 收窄，
  或退回只信本仓注册表。
- **有人为了让某个模型能用而在 `windows.py` 里加模糊匹配** ⇒ 那说明判据错了，
  该改判据，不该放宽匹配（同「屏幕守卫不许开豁免」那条）。

## 若此决策错误，修复成本是什么

**低。** 两位字段加回 `ProviderCapabilities` 是加法；`_DISCOVERERS` / `_HOST_PROVIDERS`
清空即退回今天之前的行为。**注册表本身一条都没删**（Anthropic 那 13 条还在）。

**但有一条不对称**：如果 `windows.py` 的主机名闸被放宽，
**作者的上文会按一个我们编的窗口发出去**，症状是请求被拒或稿子莫名其妙变短。
所以那一档必须有测试——`tests/test_model_windows.py` 的「自建端点/相似主机名」两条。
