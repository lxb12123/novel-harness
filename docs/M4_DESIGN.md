# M4 设计草案：增量抽取 + 事件超图 + 双 LLM 起草上下文

- 状态：**已接受（2026-08-03）**——M3 真书门槛已过、M4 解锁；实现排期在
  M2 裁决之后（M2 判负会砍起草线，本设计的双 LLM 起草部分随之调整）
- 日期：2026-08-03
- 来源：维护者设计讨论（角色图谱 / 事件化认知 / 分析+写作双 LLM / 1M 窗口滚动总结）
- 与现有决策的关系：不推翻 ADR 0004（抽取结果必须作者确认）、ADR 0005（规则不做
  语义判断；分析 LLM 是**生成功能**不是规则，不违反）；M2 考试卷面冻结不动；
  M3 是 M4 的入场券。

## 一、要解决的问题

现状的起草上下文是「矩阵/秘密/未来实体」三块**约束清单**直接塞进 prompt（X1/X2）。
它服务 M2 实验没问题，但作为产品有三个毛病：

1. 作者在界面上看到的是「must_not_reveal 清单」，不是故事——认知没有织进角色里；
2. 知识被建模成「角色 × 秘密」的矩阵，而真实的知识边界发生在**事件**里
   （谁参与了、谁知道那件事），矩阵丢了这层结构；
3. 上下文只取本场，历史背景/未出场角色的旧事没有结构化的存放与按需读取。

## 二、核心设计

### 1. 角色图谱（带档案，排除路人）

- 节点 = 角色，边 = 关系（RELATED_TO / MEMBER_OF / OWNS …，复用现有 9 类边）。
- 角色节点补**档案字段**：姓名、性别、性格、背景（含出生地）、角色设定——
  按仓库的增长规则「有消费者才加」，消费者就是起草上下文和角色卡。
- **路人不进图谱**：作者在确认抽取结果时把一次性角色标为路人，图谱只保留
  有持续戏份的角色（避免超图被「掌柜/丫鬟乙」这类节点污染）。

### 2. 事件超图：认知的正确结构

**认知不适合硬塞进图节点。** 知识是 `（谁, 哪件事, 什么时候知道）` 的三元组集合，
数学上是**时变 incidence matrix**，最自然的建模是：

```text
事件 Event {
  chapter        章节
  summary        发生了什么（结构化摘要）
  participants[] 谁参与
  knowers[]      谁知道这件事
  revealed_facts[] 这件事揭开了哪些事实
}
```

- 角色是节点，**事件是超边（hyperedge）**：一条边连着一群参与者 + 一群知情者。
- 「谁知道什么」= 角色 × 事件的 incidence；时间维沿用现有闭开区间
  （`valid_from/valid_to`，全系统只实现一次）。
- 查询变成自然的图操作：**这场在场的角色 → 他们涉及过哪些事件 → 那些事件的
  知情者是谁**。认知矩阵降级为这个超图的一个投影，不再是存储本体。

### 3. 起草上下文管线（分析 LLM + 写作 LLM）

```text
分析 LLM（便宜档）
  读新章节 → 产出结构化事件 + 角色状态更新（谁出场/谁知道什么/发生了什么）
  → 写进事件库（**作者确认**，ADR 0004 红线；确认 UI = 弹卡片逐条过）

写作 LLM（正式档）
  输入 = 在场角色 + 本场目标 + 上文
  → 按在场角色检索事件库：他们涉及的事件闭包 + 角色档案 + 相关背景
  → 组装 prompt（前提介绍更细：把检索到的角色/事件织进叙述，而不是列清单）

背景存储
  未出场但有旧戏的角色/事件 → 按相关性检索，不每章全读
  （「这场没涉及但以前埋过」的内容住在这里）

1M 窗口滚动总结
  后台把前 N 章各压成一段 rolling summary；写第 X 章时喂
  「最近几章滚动总结 + 本场角色/事件」——1M 上下文让多章后台总结第一次可行。
```

## 三、检索策略

- **按在场角色取闭包**：`subgraph(cast, hops)` 已有雏形（右栏局部关系图）；
  M4 把它从「可视化」升级成「上下文装配」的数据源。
- **新角色处理**：写作者（或分析 LLM）确认新角色不是路人 → 更新进角色图谱，
  否则只当一次性角色处理，不进图。
- **背景按相关性取**：Embedding/关键词打分取 top-K，再拼进前提介绍。

## 四、与 M2/M3 的边界

- M2 考试：225 格、三臂、裁决表**冻结不动**；本设计是产品终态，实验卷面照旧。
- M3：真书 20 章误报判定是 M4 的入场券；抽取结果的确认机制必须先在声明层
  验证过（M3 的 R2/R3/R4 就是抽取结果的校验网）。
- 成本/隐私：分析层每次读章花钱；稿子不出本机（BYOK 钥匙在本地）。

## 五、开放问题（实现前要定的）

1. 事件粒度：一场 = 一个事件，还是按「情节节拍」拆多个？
2. 作者确认的 UX：逐条卡片 vs 批量接受；路人标记怎么交互。
3. 分析 LLM 的失败率阈值：冲突 ≤2 条/章、接受率 >60%（PLAN 已预注册）。
4. 滚动总结的窗口：几章？和检索到的角色事件如何去重/排序。
5. schema 增长：事件表/档案字段都按「有消费者才加」逐条进，不一次性铺开。

## 六、实施顺序（M3 过后的建议）

1. 事件表 + 分析 LLM（先跑通抽取 → 作者确认 → 落库的闭环）
2. 角色档案字段 + 路人标记
3. 起草上下文的检索装配（按角色取事件闭包）
4. 滚动总结 + 背景存储
5. 用合成书/真书回归，量「带事件上下文 vs 不带」的起草质量（复用 M2 的判分器）
