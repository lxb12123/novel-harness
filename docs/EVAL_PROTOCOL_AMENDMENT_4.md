## 问题：这一格让 gate 恒判 INVALID

§4 的陷阱行定义：

> 每条陷阱行：`chapter`、`cast=[canonical 名]`、`goal`、`prior`（X0 上文，**不许含 tell**）、
> `reference`（一个不泄漏的完成，供天花板门用）。

把它和另外三处放在一起，四条推理，每条都逐字来自协议：

1. **tell 是「唯一生造的专名」**（§3：`血脉秘密 → 玄血蛊`；「tell 全局唯一、两两不互为子串」）。
   `玄血蛊` 这三个字不在任何模型的自然输出分布里——它是为这个实验造出来的词。
2. **X0 的 prompt 里只有三样东西**（§2）：house-style 系统提示、上文 `prior`、本场目标 `goal`。
   **零图谱事实。**
3. 若 `prior` 不含 tell、`goal` 也不含（§4 没写，但 [ADR 0010](adr/0010-writer-boundary.md) D3
   要求它不含），那么 **X0 的 prompt 里没有任何一处出现过 `玄血蛊`**。
4. 于是 `leak.score_against` 对 X0 的输出做精确子串匹配，命中率 ≈ 0 →
   **X0 的 KNOWS 泄漏率 ≈ 0 → §6 裁决表第一行「X0 KNOWS < 0.50」→ INVALID，重造陷阱。**

**而重造多少次陷阱都不会好**：这不是陷阱造得软，是 X0 物理上够不着那个字符串。
按字面执行，这份协议永远只能输出 INVALID，一次 PASS / KILL 都跑不出来。

### 它还和 §4 自己的另一句话打架

同一节的 ground truth 链：

> `import_book` 先切 12 章 → `declare_node`/`declare_alias` → `declare_knows`/`declare_believes`
> （**quote 定章号**，`valid_from` 引擎派生、绝不手填）

`declare_knows(who, secret, quote)` 靠引语**在正文里唯一命中**来派生 `valid_from`
（`declare.py:379`）。「萧决 KNOWS 血脉秘密 ch3」这条边界的引语必然是第 3 章里
那句说出 `玄血蛊` 的话——**所以正文里一定有 tell，而 `prior` 就是正文的上一段**。
一边要求 quote 在正文里，一边要求正文的上文里没有 tell，这两句话在同一节里。

### 为什么这不是「陷阱造得不够狠」

也可以想象一种设计：不给 X0 看 tell，靠 `goal` 把话题逼到那儿，赌模型自己编出一致的设定。
**那测的是另一回事**，而且协议自己已经否掉了：§3 明写「绕开 tell 的改写是**假阴性**」，
判定口径就是精确子串。模型编出的任何别的说法都不算泄漏。

## 裁定

### 裁定 A：`prior` 的禁令改读为「不许让**目标角色**已经知道它」，叙述层可以出现

**KNOWS 陷阱的 `prior` 必须让 tell 以叙述层或第三方视角出现**（否则这条陷阱不可能咬住），
**但不许出现任何表明「本条陷阱的目标角色已经知道它」的内容**。

目标角色 = 这条陷阱里那个 `KnowledgeCell.state != KNOWS` 的人。
典型形态：上一章结尾是别人的视角或叙述者交代了 `玄血蛊`，而目标角色不在场、或在场但没听见。

这正是这个产品要卖的那件事的最小实例：**上下文里有这个信息，而这个角色不该有。**
X0 不知道谁不该知道，于是顺着上文写下去；X1 被告知「苏挽 UNKNOWN 血脉秘密」，于是绕开。
两臂之间的差，**就是注入的价值**。原读法下这个差恒等于零。

### 裁定 B：`goal` 一律不许含任何 tell（§4 没写，本条补成机器判据）

`goal` 含 tell 会**强迫三臂都写它**，Δ 被压到 0——方向和裁定 A 相反，但一样让实验失效。
[ADR 0010](adr/0010-writer-boundary.md) D3 已经把它写成 review 判据；本条把它升级成
`synth/leak_selfcheck.py` 的放行条件（精确子串，零语义判断）。

### 裁定 C：FUTURE 陷阱那一侧**不适用**裁定 A，禁令照旧从严

未来实体的 tell（`血枭盟`）在**首现章之前处处不得出现**——正文、`prior`、`goal` 都不许。
这条是 §4 selfcheck 原本就有的（「未来 tell 在首现前处处不出现」），本次一字未改。

两侧不对称是有依据的，不是双标：FUTURE 的 tell **自身就是实体名**，X1/X2 的 prompt 必然点它
（`draft/context.py` 的第三节、协议 §3 都说过），所以那一侧本来就有 echo 风险，
协议因此让 `future_leak` **只作描述性地板、不主导裁决**。
在一个不主导裁决的维度上再给 X0 加一条泄漏渠道，只会让描述性数字更难读。

**后果要说清楚**：裁定 C 意味着 FUTURE 陷阱在 X0 上大概率是零泄漏，
X1/X2 反而可能因为 echo 更高。**那不是 bug，那正是这 10 条陷阱要测的东西**——
它们量的是「点名会不会反而招来提前登场」，是一个 echo 探针，不是第二个 kill-gate。
ADR 0009 报它的时候必须这么写，不许当成「注入让情况变糟」的证据。

## 为什么这一条不是在给自己开后门（必须回答）

**裁定 A 让 X0 更容易泄漏，也就让 Δ 更容易变大、更容易 PASS。**
这是三份修正案里第一次往对本项目**有利**的方向裁定（修正案 1 明确选了对自己更不利的
15/10 而不是 17/8）。所以它需要一个比前三份更硬的理由，这里给三条：

1. **另一边不是「更保守」，是「没有实验」。** 保守的选项要能跑出结果才叫保守。
   原读法下 gate 的输出集合是 `{INVALID}` 单元素——它不构成对任何主张的检验，
   既不能证实也不能证伪。**一个永远判 INVALID 的 kill-gate 不是严格，是坏了。**

2. **协议自己的两道门把滥用夹住了。** 裁定 A 的自由度是「prior 里 tell 出现得多显眼」，
   而 §6 第 1、2 行规定 X0 的 KNOWS 泄漏率必须落进 **[0.50, 0.90]**：
   造得太软 → 撞地板 INVALID；造得太狠（prior 直接把话喂到嘴边，X0 必写）→ 撞天花板 INVALID。
   **这两道门本来就是为「陷阱强度」设的，而陷阱强度正是本裁定动的那个旋钮**——
   也就是说，协议早就预料到有人要调它，并且预先规定了合法区间。本裁定没有碰那个区间。

3. **三臂对称。** 同一份 `prior` 逐字节喂给 X0/X1/X2（ADR 0010 D4：三臂共用同一个 base）。
   裁定 A 加进去的信息三臂都有，它对 Δ 的贡献是零；变的只是「有没有东西可漏」。
   §3 论证假阴性时用的是同一个对称性论证。

**最后一条，也是最重要的一条**：如果实测发现 X0 的泄漏率落在 [0.50, 0.90] 之外，
按协议就是 INVALID + 重造，**而重造时只能调 prior 的显隐程度，不许调那两个阈值**。
阈值仍是 `0393088` 冻结的原值，本修正案一个字没碰。
