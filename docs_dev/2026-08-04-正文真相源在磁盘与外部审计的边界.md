# 2026-08-04 正文真相源在磁盘，外部对接只能是「导出式审计」

> 给以后的自己：动到「正文 / DB / 云」这三者关系之前先读这一份 + ADR 0007。

## 决定了什么

1. **正文的真相源永远在磁盘 Markdown**（ADR 0007），`book.db` 只是图谱 / 证据 /
   决策日志 / 调用审计的**索引与审计层**，**不是正文副本**。磁盘先写、DB 跟着走
   （`importer.sync`），DB 永远不回答「正文是什么」。
2. 未来任何外部服务对接（审计 / 云同步 / 多端）都必须是**作者显式发起**的
   **导出式对接**：桌面照常本地跑，需要时把审计数据推给外部；运行时零外部依赖。
3. SQLite 不是「没有数据库」，是「数据库就是这份文件」：图、证据、日志、审计
   在同一份 `book.db` 里同事务一致，这是桌面形态下最强的审计保证。

## 为什么

- **隐私是卖点**：「你的书永远不离开你的电脑」只有本地跑才说得出口且是真的。
- **分发形态定了 C 方向**（桌面安装包），作者机器上不可能装数据库服务；Neo4j /
  Postgres / Qdrant 在 v1 全部砍掉（ADR 0001 / 0002），图谱是 SQLite 里的
  `node` + `edge` + `alias`。
- **审计本来就可以被外部验证**，不需要运行时依赖：
  - `decision_log` 追加式、触发器拦改写/删除（迁移 003）；
  - evidence / prompt / 输出全部 sha256 内容寻址，外部可逐字节复核；
  - 提案 outbox + 审计信封：先提交业务、后补日志，崩了能恢复；
  - `runs/*.jsonl` 全证据重建，离线可重算。

## 对接外部审计的具体方式（今天的事实）

- **最省事**：外部直接读 `book.db`（SQLite 文件）——它就是完整审计源。
- **Neo4j / Postgres**：作为**审计消费端**导入做分析（关系变迁史、supersede 链、
  超边投影），不改桌面架构。
- 自然的桥：`nh audit-export`（决策日志 + 证据哈希 + run 记录 → 一份可验证的
  审计包）。**还没做**，等审计方案定了再动手。

## 红线

- 任何「**自动上传 / 云同步**」都会引入**正文第三副本**（磁盘 + DB + 云端），
  那要先**改 ADR 0007 再写代码**；上传必须显式作者动作并明示隐私影响。
- 测试 / 验收**不许污染真书库**。本次（2026-08-04）验收后已把抽取产物
  （runs / proposals / edges / evidence）清回测试前状态；`chapter_summary` 与
  对应的 `model_call` 审计是**功能数据**（滚动总结已跑第 1–100 章），不是垃圾。
- 真书库的 schema 已迁到 v4（新增 `chapter_summary` 表），这是跑滚动总结的必要步骤。

## 什么情况下要推翻它

- 多人合著 / 多端同步成为真实需求（要认证 + 多租户，那是另一个产品形态）；
- 作者明确要求云端备份且知情同意——即便如此也要先改 ADR，再写同步代码。
