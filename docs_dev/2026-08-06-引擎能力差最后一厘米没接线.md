# 2026-08-06 盘点：引擎的能力差「最后一厘米」没接线

**决定了什么**：给「作者说 AI 起草写出来的小说很一般」找到了**机械原因**，
并把病命名为**「最后一厘米」**——能力建完了、有测试、被文档记着，
但**作者触达不到它**。今天一次盘出三处同形状的，它们叠加起来正好解释那个体感。

同时定下：模式二的工具表要**长出推进侧**（生成可能性），不能只有约束侧（禁止清单）。

**为什么**：起因是我给了一张七个工具的表（resolve / constraints / read / mentioned /
draft / checks / save），作者一眼看出问题：「如果就是这些工具，写不出好的小说，
我做那么多矩阵图谱就是为了写的时候能推进情节」。他是对的——那张表全是「别写错」，
一个「接下来写什么」都没有。于是跑了三路盘点查仓库真实状态。

---

## 一、最狠的一条：唯一在算认知不对称的代码，方向是反的

`src/novel_harness/draft/product_context.py:94`，安全谓词 `_is_writer_safe`：

```python
cast_ids <= knower_ids     # 在场的人必须全都知道这件往事，才让它进 prompt
```

**它的补集就是戏剧张力**：

```python
cast_ids - knower_ids      # 在场的人里有人不知道这件往事 ← 这就是这一场的戏
```

同一个 frozenset 运算，换个符号方向，就从「安全过滤器」变成「张力发生器」。
**今天：有人不知道的往事 → 丢掉。**

全仓 grep `tension` / `asymmetr` / `张力` / `不对称`，生产代码里**零命中**
（只有两处把「不对称」用作行文措辞）。**素材全在，归约一个都没写。**

## 二、三个「最后一厘米」，叠加 = AI 起草没有记忆

| # | 能力 | 断在哪 |
|---|---|---|
| 1 | 事件记忆 + 人物档案 + 滚动总结（`build_product_context`） | **只在 `form=PRODUCT` 时装配**（`api/app.py:1153`） |
| 2 | 同上 | **前端硬编码发 `form: "X1"`**（`DraftDrawer.tsx:46`），测试还钉住了 |
| 3 | 滚动总结 | **没有任何 HTTP 端点**，唯一入口是 `nh summarize` CLI（维护者手跑、会花钱）→ 新库里 `chapter_summary` 表恒空，【更早章节滚动总结】永远渲染成「- 暂无」 |

**结论：在工作台点「AI 起草」，走不到 `build_product_context`。**
模型拿到的只有「上文 800 字 + 在场名单 + goal + 一串禁令」。

**这就是「写出来的小说很一般」的直接原因。** 记忆层建好了，界面没接线；
和一个裸模型的差别只剩「少说破几个秘密」。

## 三、R2 / R3 在作者手里是死的（**但这不削弱 M3 判定**）

| 规则 | 判据字段 | 谁能写这个字段 |
|---|---|---|
| R2 未来实体提前出现 | `props.first_appears_chapter` | **没有人**。CLI 七条 declare 子命令、HTTP `DeclareNodeBody`、前端输入框，**一处都没有**。全仓唯一写入者是 `synth/build.py` 和 `synth/m3_replay.py`（仪器，不是产品） |
| R3 死人说话 | `is_dead` ⟸ `value_key == "dead"` | **没有人**。`value_key` 全仓零写入方；`declare_state` 未做（`declare.py:32` 明写） |
| R3 未登场者开口 | 同 R2 | 同上 |
| R4 地点冲突 | 场景块 `<!-- nh: loc= -->` | 作者手写，**活着**，但不写场景块它就永远沉默 |

**我第一反应说这「削弱 M3 的判定」，那是说过头了，更正掉：**

`M3_GATE_PROTOCOL.md` §五逐字写着「两本书都是干净文本，**规则未开火**——
这一腿量的是『规则在真书正文上不误报』；『该响时响』由合成考卷 25/25 证明」。
**两腿分工写得清清楚楚，协议没骗人，判定成立**，合成那腿还可复现
（`uv run python -m synth.m3_replay`，边界数据运行期内存叠加、不落库）。

准确的说法是：**这是 capability gap，不是 verdict gap。** 规则会响（合成考卷证明了），
但**作者喂不进让它响的数据**。附带一条：那次真书跑的「30 角色花名册 + 17 首现章进图」
是怎么进去的——**那个脚本不在仓库里**（`scripts/` 只有 demo / probe /
roster_coverage / seed_demo / watch_gate），所以那次跑不可复现。

## 四、作者那份旧设计（很久以前聊的）——大部分已经实现了

| 他当年的设计 | 今天 |
|---|---|
| 角色字段：性别 / 性格 / 背景 / 角色设定 | ✅ `CharacterProfileView{gender, personality, background, character_notes, main_character}` |
| **认知用「事件集合」表示，含「谁参与 / 谁清楚」** | ✅ **他赢了一半**：`EventView{event, participants, knowers, revealed_facts}` —— 两个字段本来就是分开的 |
| 按涉及角色读取图谱 | ✅ `events_for_characters(character_ids, chapter)` |
| 没涉及但属于背景的 | ✅ `background_events`（上限 12） |
| 总结放进提示词前提介绍 | ✅ `render_product_memory` 就是第一条 system 消息 |
| 双 LLM（分析 + 写作） | ✅ `RollingSummarizer` 吃 analyzer |
| 角色之间连线 | ⚠️ schema 有 `RELATED_TO`，**`declare_related` 没做**；且无向，「A 是 B 的师父」表达不了 |
| 不含路人 | ✅ ADR 0018 已是这个形状 |

**他的直觉当年就对，问题从来不在设计，在没接线。**

两处他比现在的实现更对：

1. **`event_participant` 表不是时态的**（主键只有 `event_id+character_id`，没有
   `valid_from`/`valid_to`/`scope`/`status`），只有 `event_knower` 五列齐全。
   所以事件层的「在场」是永恒事实——跟「细粒度包含在事件里」的想法冲突。
2. **未来事件表示不了**：`ProvisionalEventSpec` 强制要 `evidence_id`；
   `PLANNED` 边被三处断言挡在读路径外（`store.py:86` / `sqlite_store.py:134` /
   `panel/knowledge.py:84`）。**「作者打算怎么解」引擎今天一个字读不到。**

## 五、可算但没人算的东西（全部纯集合运算，不撞 ADR 0005）

盘点列了 15 条，最有价值的六条：

| 能算什么 | 靠什么算 |
|---|---|
| **A 知道、B 不知道、两人同场** | `KnowledgeState` 三态按列分区（`models.py:160`） |
| **B 持有会被当场戳破的错误信念** | `believed_value`（`models.py:649`），可直接进 prompt |
| **瞒了多久**（A 在 ch88 知道，现在 ch152 = 压了 64 章的雷） | `since_chapter`（`models.py:641`），纯减法 |
| **可摊牌的秘密**（在场全员已知）| `must_not_reveal` 那个 `any()` 的**取反**，今天没有函数产出它 |
| **有人知道有人不知道的往事 + 说破它会揭掉哪条秘密** | `product_context.py:94` 取反 × `EventView.revealed_facts` |
| **下一个登场倒计时** | `constraints.py:325` 的排序键，今天只被渲染成禁令 |

## 放弃了什么

- **放弃了「R2/R3 空转削弱 M3 判定」这个说法**——我自己的第一反应，核实后不成立。
  协议诚实，两腿都有记录。**记下来免得下次又拿它当论据。**
- **放弃了「工具表 = 检索 + 校验」这个模型**。那正是作者一眼否掉的东西。
  引擎的活是把「此刻手上有哪些牌」摆出来，不是替作者选，也不只是拦着他别打错牌。
  （对应 `panel/__init__.py` 那句「它不说『你错了』，它说『这是你告诉过我的』」——
  推进侧的说法是：**它不说「接下来写这个」，它说「此刻你手上有这些牌」**。）

## 什么情况下要推翻它

- **「最后一厘米」这个诊断**：如果把前端改成发 `PRODUCT`、补上滚动总结端点之后，
  作者仍然觉得起草质量没变，那说明病因不在接线，在别处（prompt 形状？模型？长度档？）——
  **那时别继续接线，回头重新找病因。**
- **推进侧工具**：如果做出来之后作者发现「牌太多，反而不知道打哪张」，
  说明归约还不够——那时要的是**排序**（哪条张力最该用）而不是更多条目。
  但排序很可能是语义判断，会撞 ADR 0005 铁律，届时要重新裁。
