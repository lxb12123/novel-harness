## 1 · 滚动总结调度 —— **已定**

一个排队用的分数被当成了准入门槛；「没有总结」和「总结是旧的」被当成了同一个问题。

方案见 [`2026-08-22-滚动总结调度去阀门与补缺覆写解耦.md`](2026-08-22-滚动总结调度去阀门与补缺覆写解耦.md)。
里面钉了三条不许弱化的：定期扫描是主路（保存不是必需）、权重只分名额、撤回的不算缺。

**2026-08-22 已裁定：改过的章自动重新总结并覆盖**（覆写单真去重买一份，不是"只提示"）。
理由是防抖 + 幂等已经把「改个错别字就重新买一次」挡住了，且 ADR 0030 原文就写着
「新正文的机器总结可以正常替换它」。**这一条此前写的是「范围里明确不含、倾向只提示」，已作废。**

## 2 · 续写只用了 2% 的窗口 —— 小，建议先做

后端本来会按模型窗口算能给多少上文（200k 的模型算出来是 16,333 字），
**但前端写死了 1,000 字，不问后端要**。换多大的模型都是 1,000。

作者这一章写了 4,000 字还是 100,000 字，AI 拿到的都是最后那 1,000 字。

数字见 [`2026-08-22-模型窗口各槽额度与前端硬上限.md`](2026-08-22-模型窗口各槽额度与前端硬上限.md)。

**这是纯修 bug**，不是加功能：后端那套按窗口伸缩的设计今天被前端架空了。
建议第一个做——做完之后第 3 条的收益才看得出来（现在 1,000 字的池子里，加不加总结都看不出差别）。

## 3 · 续写拿不到前面章节的总结 —— 中

续写送给模型的全部内容是 404 个字符：一段固定的写作提示、光标前的 1,000 字、
一句「在场：未知」、一句「顺着往下写」、几个不许写的名词。

**没有前面章节的总结、没有已确认的事件、没有人物档案**——库里全都有，一条没送。
跳过的理由写在代码注释里是**延迟**（「停手 400 毫秒就要出结果，查这些太贵」），不是正确性。

整章起草那条路本来就在用这些，管道现成。要定的是**哪几格便宜到能进 400 毫秒这条路**：
总结那一格是纯查库（158 章约 19,000 字，不额外花钱），事件和档案要查图要算。

## 4 · 改老章之后没有锚定 —— 中，但有免费的一半

作者跳回去改第 2 章时，AI 完全不知道第 3 章之后存在，写出来的东西可能和后面直接打架。

**好消息：一半已经在跑，而且结果被扔掉了。**

每次保存，系统已经在做一件事——把这一章里「依据是旧正文」的那些自动抽出来的事实
全部标成"停火"，并算出一份精确清单（退了哪几条、其中几条是写作时会用到的）。
**但调用它的那一行没接返回值，那份清单算完就没了。**

这份清单是**确定性的、纯查库的、免费的**。接住它就能变成一句话告诉作者：

> 「你刚改的这一段，原本支撑着 3 条已确认的事实，它们现在失去了依据。」

它答不了「你写的这段跟第 3 章矛盾吗」（那是语义问题），
但它能答「你刚删的那句话，是后面某些设定的唯一出处」——而这恰恰是改老章最容易出事的地方。

## 5 · 写完之后没有任何内容检查 —— 大

续写回来之后**只验一样：字数**。落在 60–260 之间就算过，少了补一次。

没验：有没有真把秘密写破、有没有写到还没登场的东西、跟前面接不接得上、跟后面矛不矛盾。

**这不是疏漏，是结构上做不到**——仓库里有一堵墙，禁止写作那一侧调用判泄漏那一套
（那堵墙保护的是实验的可信度）。代价就是产品这一侧没有事后检查。

真要做，方向是「写完之后用模型比对新正文和后面章节的总结，只告警不阻断」。
**这个口子 2026-08-17 已经开好了**（ADR 0030 对「规则不做语义判断」开的窄例外），
而且已经有一个模块在跑这个形状（比对总结和正文），换一对输入就是。

## 6 · 「作者永远在书的最前沿写」—— **已裁定：这个前提不成立**（这条最重要）

> **2026-08-22 更正**：本节标题原来写着「待裁定」，与上面那张表的「已裁定」打架。
> **以表为准：已裁定，前提不成立。** 落地方案就是轨道那一份，不另开裁定文书。
> 第 4、5 条按轨道那份的方向做。

这个前提**写在三个地方的代码里，没写在任何一份文档里**，所以从来没被审视过：

- 权重算的是「离作者当前那一章多远」，章号更大的一律当成"还没写"，权重 0；
- 拼 prompt 时只取「比当前章更早」的总结和事件；
- 续写的上文只有「光标之前」，同章之内。

作者跳回去改老章时，这三条**同时**失效：后面那些章不是未来，是已经写完的正文。

**这不是三个 bug，是同一个前提的三个投影。** 第 1、3、4、5 条都是它的下游。
定了它，那几条的方向才定得下来。

## 7 · 作者声明的事实被标成「机器推演」 —— 小，**已定方案**

写作简报里每条事实都标着出处。**八类出处塌成两个标签，而且是七比一：**

```
AUTHOR_INTENT       → 「作者确认」     ← 只有这一类
AUTHOR_CANON_FACT   → 「机器推演」     ← 作者经声明链确立的
AUTHOR_BACKGROUND   → 「机器推演」     ← 作者手写的
EXTRACTED_CURRENT   → 「机器推演」
OBSERVED_TEXT       → 「机器推演」
MACHINE_SUMMARY     → 「机器推演」
MACHINE_INFERENCE   → 「机器推演」
UNKNOWN             → 「机器推演」     ← 它的定义是「不得补写成事实」
```

实跑出来的样子（这一条我造数据时标的出处是 `AUTHOR_CANON_FACT`）：

```
- 苏挽 位于 断魂崖下（机器推演 · 硬依据）
```

**「机器推演 · 硬依据」读不通**——机器猜的东西怎么会是硬依据。
两半来自两个字段：前半是出处，后半是强度。**强度是对的，出处标错了。**

### 病根：一个标签在两处用，一处只要出处，一处要出处 + 强度

塌成两档是为了后一处方便，代价是前一处骗人。
**出处和效力是两件事**——效力已经由另一个标签（硬依据 / 参考）负责了。

### 今天的受害者只有模型（2026-08-22 复核）

**这份简报作者看不到。** 他只看到一行进度「封存写作简报（第 2 章），好了」，
简报正文只进模型的 prompt。所以今天的后果只有一条：
**模型被告知这是"机器推演"，会低估一条其实是作者亲口确立的事实。**

方向是保守的（把作者的说成机器的，不会造成越权），所以不是安全问题。
**但趁它还没上屏时修最便宜**——按「右栏由 LLM 无感生成、作者可见可改」的方向，
它迟早会到作者眼前，那时作者会看到自己声明过的事实被标成"机器推演"。

### 要做的：出处分五档，只表出处，不表效力

```
作者确认   ← AUTHOR_INTENT                                  作者当场点头的
作者记录   ← AUTHOR_CANON_FACT / AUTHOR_BACKGROUND          作者写下的
机器有据   ← EXTRACTED_CURRENT / OBSERVED_TEXT / MACHINE_SUMMARY   从正文来的
机器推演   ← MACHINE_INFERENCE                              真正的猜测
未知       ← UNKNOWN                                        不得补写成事实
```

**`UNKNOWN` 尤其不能再标成「机器推演」**——它的定义是「缺数据、陈旧、被截断、
歧义或当前能力不可回答，**不得补写成事实**」，标成"推演"会让它看起来像一条弱事实，
而不是一个洞。

### 补一条测试

**今天没有任何测试钉这个二分**——也就是说没有人决定过"八类只显示两类"，
它只是那个渲染函数顺手写成了这样。

修完要留一条：**每一类出处都有自己的标签，且作者来源的三类里没有一类会渲染成"机器"。**
（同第 8 条的规矩：改完留一条守卫，否则过几个月会被顺手改回去。）

### 改完要看一眼模型行为

这是"给模型看的措辞"，改了之后那些事实的权重在模型眼里会变。
**不是回归风险，是预期效果**——但要确认它变的方向是对的（作者的事实被更当回事，而不是相反）。

### 记一笔：「未知 · 参考」读起来拗口 —— **本条范围外，不做**（2026-08-22 裁定）

出处改成五档之后会印出 `（未知 · 参考）` 这种组合：出处是「未知」，强度却是「参考」。
今天它真的会出现——`calibrate.py` 里 `first_appears_chapter is None` 的 APPEARED 事实
kind 是 `UNKNOWN`，而 `writer_visibility` 不是 HIDDEN，于是带着 SUGGESTION 进简报。

**要修就得给「未知」那一档单独去掉强度后缀，而那是动「强度」那一半。**
本条只管**出处**，强度是另一件事，混在一起改会让 review 分不清哪个改动带来了哪个后果。
**记在这儿，这一轮不做。**

## 8 · 跨层的数字没有守卫 —— 小，但这条是元问题

今天撞了**三次同一个形状**：

| 两层各有一个判据 | 谁赢了 |
|---|---|
| 前端上文上限 1,000 ↔ 后端按窗口算的额度 | 前端 |
| 调度器的权重门槛 ↔ 注入侧的字数预算裁剪 | 调度器 |
| 「有没有总结」↔ 「总结是不是旧的」 | 粗的那个 |

三次，同一个病：**没有任何一层"拥有"那个数，也没有任何测试跨在缝上。**
每一层内部都写得仔细，两层之间没人负责，所以后加的那一层总能悄悄赢，而且不会红。

仓库里已经有一条同形状的纪律（前端产物目录 ↔ 后端读取路径，专门一条测试钉着，
注释写着「它坏掉时没有任何别的东西会红」）。**那条纪律是对的，只是只用在了一处。**

### 这三条各归各家 —— 不是新工作，是同一批工作的另一种数法

| 缝 | 定下来的正确算法 | 归哪个任务 |
|---|---|---|
| 前端 1,000 ↔ 后端按窗口算 | **公式只有后端一份**，前端不判断，那个数跟着设置返回给过来 | 任务 2 |
| 调度器权重门槛 ↔ 注入侧裁剪 | **权重只分名额，不当门槛**；裁剪归注入侧，判据是字数不是章距 | 任务 1-A |
| 有没有 ↔ 旧不旧 | **两个判据各自独立**，同一次扫描问两个问题、下两种单 | 任务 1-B |

### 修完之后每处留一条守卫

不留的话，过几个月同一处会长出第二个数。

- 任务 2 —— 钉「前端那个上限 ≥ 后端在任何模型下算出的最大值」
- 任务 1-A —— 钉「候选池里不会因为距离远而少人」
- 任务 1-B —— 钉「**扫描器说排了覆写 = 单里真的带着总结那一项**」

最后这条特别值钱：今天那个 bug 的表现就是"报了但没做"——
**报什么和做什么之间，今天没有任何东西对过。**

### 为什么这个病特别容易犯

**因为两边各自看都是对的。** 前端写 1,000 的理由是「别把整章塞进请求体」——合理；
后端按窗口算的理由是「大模型该多给」——也合理。

**没有任何一边是错的，错的是它们不知道对方存在。**
而代码审查看的是一个文件、一次改动，天然看不见缝。**只有测试能站在缝上。**

## 11 · 那道「逐字节冻结」的守卫没在守 —— **已定方案**

`test_calibration_eval_guard::test_three_arm_assembler_is_byte_identical`
自称把 `draft/assemble.py`（三臂共用的渲染器）逐字节冻住。**实测（2026-08-22）：**

```
未提交时改 assemble.py  →  守卫红
提交之后再跑            →  守卫绿
```

它用的是 `git diff --exit-code`，只比「工作区 vs 已暂存」。
**拦得住「顺手改了忘了看」，拦不住「改了并且提交」**——而真要改考卷的人当然会提交。

**做法**（并入 M1-a，那一条正好要动这个文件）：
守卫从「有没有未提交改动」换成「**这个文件的内容哈希等不等于登记的那个**」，
M1-a 落地时同一笔更新那个哈希。
此后每次改 `assemble.py` 都必须显式动那个哈希，**改卷子这件事再也藏不住**。

**它和第 8 条是同一类病**：有一道看起来在守的东西，其实没在守。
第 8 条是「两层各有一个数、中间没人管」，这一条是「有人管，但那个人在打盹」。

## 9 · 三处花钱，作者都不知情 —— 记录在案

| 什么时候 | 频率 |
|---|---|
| 保存之后自动生成滚动总结 | 每章一次 |
| 保存之后自动抽取 | 每章一次 |
| 停手 400 毫秒自动续写 | 随时 |

外加：**工作台开着没人动，每 30 分钟也会自己花一次钱**（后台自治，默认开）。

代码里防的是「重复付费」（幂等、防抖、默认不问），**防的不是「作者不知道自己在付费」**。
这是 BYOK——花的是作者自己的钱。
