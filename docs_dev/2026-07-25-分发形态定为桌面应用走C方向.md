# 2026-07-25 分发形态定为桌面应用（C 方向）

> **下次回来先看这一份。** 它回答三件事：最终形态是什么、今天走到哪、没做完的长什么样。
> 工程约束在 `docs/`，这里记的是**为什么这么定**。

---

## 决定了什么

**最终形态是 C：小说作者下载一个桌面安装包，双击就用。** 不做服务器部署、不做 SaaS。
开源保留，愿意折腾的人 `git clone` 自己改。

```
小说作者    下载 .dmg / .exe → 双击 → 开窗口
            电脑上没有 Python、没有 Node、没有终端
            书在自己磁盘上，库在自己电脑上

fork 的人   git clone → uv sync → npm install → 两个终端跑 dev
            他不需要桌面壳

我自己      日常 = 和 fork 的人一模一样，发版时才多一步打包
```

## 为什么

1. **产品命题不允许别的。** 目标用户是「用 WPS 不想碰命令行的作者」。要部署就得装 Docker
   或 Python、改配置、看日志——**任何一步要开终端 = 这个用户流失**。
2. **ADR 0007 已经定死正文在磁盘上。** 本地跑天然满足；一上服务器就要重新回答
   「哪一份是真相源」，那是要改 ADR 的事。
3. **隐私是真卖点。** 小说作者对未发表稿子极敏感。「你的书永远不离开你的电脑」这句话
   只有本地跑才说得出口，而且是真的。
4. **开源 ≠ 用户必须自建。** Calibre、Anki、Zotero、Logseq 全是开源，全是下载安装包。
   自建能力留给愿意折腾的人，不是塞给所有人的作业。

## 放弃了什么

- **服务器多用户部署（SaaS）。** 现在的架构根本不支持：`api/app.py` 零认证零 CORS 零 user
  概念（27 条路由全裸奔，挂公网 = 谁都能读写别人的书）、`NH_DB` 单库单租户、SQLite 单写者、
  而且撞 ADR 0007。**要做那是另一个产品**，不是这个仓库的默认形态。
- **Docker 单用户自托管。** 技术上很便宜（加个 Dockerfile 就行），但目标用户不会用 Docker，
  等于为零个真实用户维护一条路径。以后真有人要再说。
- **现在就做桌面包。** 见下面「为什么先不做 C」。

## 什么情况下要推翻它

- 出现真实需求：多个作者要共用一本书（合著）。那时才谈认证和多租户。
- 或者：桌面包的签名 + 三平台 CI 成本被证明高到不值，那就退回 B 档（一条命令），
  像 A1111 那样长期停在「装个 Python 就能跑」。

## 结构：不是三条路径，是一个洋葱

这是这次讨论里最要紧的一条认知——**维护成本不是 3 份，大约是 1.3 份**：

```
桌面包          = nh serve + 一个窗口                      几十行（还没写）
  └ nh serve      = 挑端口 + 起 uvicorn + 开浏览器           已落地 ✅
      └ api/app.py  = 引擎的 HTTP 壳（27 条路由）             已有
      └ cli.py      = 引擎的终端壳（15 个子命令）             已有
          └ src/novel_harness/  引擎 = 唯一真相                已有
```

`api/app.py` 第一行的 docstring 自己写了这条纪律：**「只把引擎函数包成 HTTP，不装业务。
不碰连接。」** 只要它守住，加一个功能 = 引擎写一次 + 两个薄壳各转一次。

**真正的双份只有一处：前端 ↔ 后端契约。** 后端加一条路由，前端要写 UI 调它，而且现在没有
运行时测试保护（CI 现在会跑 `tsc -b`，所以类型错会红；但出参语义改了照样静默坏）。

**CLI 的定位建议降级**为「引擎的调试出口 + 心跳载体」，不再承诺和 GUI 功能对等——
它的价值从来不在小说作者身上（他们不碰终端），而在 `demo.sh`、测试和 debug。
一旦这么定，「CLI 少个功能」就不算 bug，省掉未来所有纠结。**这条还没写进 README。**

## 平时怎么测：三层，别混

### L1 日常开发（每分钟）—— **99% 的时间都在这儿**

```bash
uv run nh serve --db book.db --no-open    # 只为建库，看到 URL 就 Ctrl-C（一次就够）
NH_DB=book.db uv run uvicorn novel_harness.api.app:app --port 8000 --reload   # 终端 1
cd frontend && npm run dev                                                    # 终端 2 → :5173
```

改一行 `.tsx`，浏览器 0.1 秒自己刷新；改一行 `.py`，后端自己重启。
**端口必须是 8000**——那是 `vite.config.ts` 里写死的代理目标。

⚠️ **别用 `nh serve` 做日常开发**：它没有 `--reload`，而且它自己就发前端，发的是上一次
`npm run build` 的旧产物 → 你会对着一个不会更新的页面改代码。

### L2 集成验证（每周）—— 验「打包之后还对不对」

```bash
cd frontend && npm run build && cd ..     # 产物落 src/novel_harness/webui/
uv run nh serve --db book.db              # 一个进程，自动开浏览器
```

它专门拦「开发时好好的、打包后就坏」那一类：静态资源路径、刷新页面 404、生产构建下的
接口契约。这些在 L1 **永远测不出来**，因为 Vite 在中间兜着。
比喻：L1 是在 Word 里编辑，L2 是导出成 PDF 看一眼排版有没有乱。

### L3 发布验证（发版）—— 验「别人电脑上跑不跑得起来」

```bash
cd frontend && npm run build && cd .. && uv build
uvx --from ./dist/novel_harness-*.whl python -c "import novel_harness.api.app as m; assert m.webui_built()"
```

关键是**要在没装过 Python 的机器上测**——你的开发机装了一切，本机永远测不出「用户电脑上
缺 XX」。CI 的 packaging job 现在每次 PR 都在干净 runner 上跑这个。

## 今天（2026-07-25）做完了什么

### ① 前端产物随 wheel 分发

- **产物位置从 `frontend/dist/` 改到包内 `src/novel_harness/webui/`**（`vite.config.ts` 的 outDir）。
  理由只有一条：**实测确认 `uv_build` 会把模块目录下的任何文件打进 wheel（非 `.py` 也进），
  但它不支持从模块外 force-include**。落在包内 = `uv build` 自动带上前端，不用养 build hook。
- `api/app.py` 的 `_DIST` 从 `parents[3]/"frontend"/"dist"` 改成 `parent.parent/"webui"`。
  **旧写法的坏法是无声的**：源码树里跑得好好的，装进 site-packages 后 `parents[3]` 指向
  site-packages 的上一层，那儿没有 `frontend/` → 工作台静默降级成只读原型，`/` 照样 200、
  不报错、CI 全绿，只有作者看得见。
- 新增 `api/app.py::webui_built()`，`nh serve` 用它在没构建时打一行黄字警告。

### ② `nh serve`

`nh serve --db book.db` = **建库 + 起服务 + 挑端口 + 开浏览器**。要点：

- **库不存在就建**（`api/deps.py` 拒绝连不存在的路径，怕 sqlite 悄悄建空库给出假矩阵），
  于是 `frontend/README.md` 里那句手敲的 `python -c "... migrate ..."` 没了。
- **端口被占自动换**，不报错退出——作者要的是打开工作台，不是学什么是端口占用。
- **先绑 socket 再交给 uvicorn**（`Server.run(sockets=[...])`），不是「探测再让 uvicorn 绑」：
  后者在 close 和 bind 之间有窗口，端口可能被抢走，而我们已经把它印出来了。
- **stdout 只有一行 URL**（同 `nh init` 的纪律）。以后桌面壳就是读这一行知道窗口指向哪儿。
- **默认只听 127.0.0.1**。没有认证，库里是未发表的稿子，`--host 0.0.0.0` 得自己敲。

### 守卫（这次最值钱的部分）

打包路径坏掉时**没有任何自然产物会红**，所以必须把它直接写成断言：

- `tests/test_serve.py::test_webui_lives_inside_the_package` —— 产物必须在包内
- `tests/test_serve.py::test_vite_outdir_and_dist_agree` —— **Vite 写到哪**（ts）和
  **FastAPI 从哪读**（py）是两个分处不同语言的字面量，中间没有任何东西连着。改一个忘一个，
  结果是 wheel 里没有前端，而整套测试照绿（测试套件从不构建前端）。
- `ci.yml` packaging job 三级：① wheel 里有产物 ② 包装得上 ③ 装完之后 `webui_built()` 为真。
  **③ 才是 `_DIST` 那个 bug 的原形**——①② 全绿，作者打开是一张只读原型。
- 白捡的一层：packaging job 现在跑 `npm run build`（含 `tsc -b`），**TS 类型错从今天起会红**。

测试 601 → 608 全绿，`demo.sh` 心跳绿。

## 没做完的架构长什么样

按依赖顺序，**上面两条不依赖任何未定的东西，下面几条都有前置**：

```
✅ ① 前端进 wheel
✅ ② nh serve
────────────────────────────────────────────────────────
⬜ ③ 启动脚本 start.command / start.bat        A 档过渡，成本近零，随时能做
────────── 下面这些建议等 M2 kill-gate 出结果 ──────────
⬜ ④ provider 的配置文件路径（API key 入口）
⬜ ⑤ pywebview 桌面壳 + release.yml 三平台 matrix
⬜ ⑥ 代码签名（要花钱那步）
⬜ ⑦ 前端 smoke test（堵住唯一真双份）
```

### 为什么先不做 C（桌面包）

**业界同类产品在这个阶段没有一个是先做桌面包的。** ComfyUI 在 A 档（clone + `python main.py`）
跑了近两年、成了行业标准工具之后才出 Electron 桌面版；JupyterLab 到今天大部分人还在用 B 档。
原因是 C 的隐藏成本远超打包本身：签名（Apple $99/年，Windows 更贵）、三平台 CI、
自动更新通道、崩溃上报、版本迁移——**这些只有在真有用户时才划算**。

两个前置条件：
1. **M2 kill-gate 通过** —— 判负要砍起草线，产品定位改成「作者的记忆外挂」，那时连
   API key 入口都不需要了，桌面壳的形态也会变。
2. **有真实用户在用 A 或 B** —— 没用户就做签名和自动更新是纯浪费。

### 桌面壳选型（决定了，但还没动手）

**PyInstaller + pywebview**，用系统 webview（macOS WKWebView / Windows WebView2），
不带 Chromium，约 50MB。选它是因为**它就是 `nh serve` 加一个窗口**：

```python
port = pick_free_port()
threading.Thread(target=lambda: uvicorn.run(app, port=port), daemon=True).start()
webview.create_window("Novel Harness", f"http://127.0.0.1:{port}")
webview.start()
```

排除了：Tauri + Python sidecar（体积最小观感最好，但要引入 Rust 工具链，Python 还是得
PyInstaller 打一遍）、Electron（~150MB+，带整个 Chromium，没必要）、
Briefcase（工具链更完整但学习曲线陡）。

**三个坑提前记着**：① 不签名的话 macOS Gatekeeper 会直接说「已损坏，无法打开」，不是警告
是拒绝；② PyInstaller 不能交叉编译，Mac 包必须在 Mac 上构建 → `release.yml` 要加
`strategy.matrix`；③ 桌面用户设不了环境变量，`provider.py` 现在只从 `os.environ` 读
（`ProviderConfig.from_env`），必须加「配置文件优先」的路径，**不改这个桌面版的起草功能就是死的**。

## 还没定的三个决定

1. **作者的库默认放哪。** `uvx novel-harness` 至今是 stub，卡的就是这个——它不带 `--db`，
   得自己知道去开哪个库。**这个默认位置一旦发出去就很难改**（同 ADR 0007 里 `root_path`
   存绝对路径的教训：路径进了库，库就不可搬家）。定了它，stub 才能接上 `nh serve`。
2. **LLM 调用走谁的钱。** BYOK（作者自填 key，我零成本，但非程序员不知道去哪申请）
   vs 我做中转（注册就能用，我付 API 费）。`provider.py` 是 OpenAI 兼容协议，
   **中转是免费送的能力**——把 `NH_LLM_BASE_URL` 指过去就行，一行代码不用改。
   建议：GUI 里做设置页让作者粘贴 key，默认 BYOK，中转当可选付费便利。
   不管走哪条，**出去的只是当前场景的 prompt，不是整本书**——这正是项目已有的设计
   （完整 PLANNED 禁止进 prompt），值得写在首页。
3. **CLI 要不要正式降级。** 见上面「洋葱」那节。写进 README 一句话就能省掉未来所有纠结。

## PyPI：**有意推迟**（同日决定，别当成漏了）

`novel-harness` 至今 404，但**包名还没最终定**，而 PyPI 是先到先得、**不能改也不能转让**的
（想换名只能重发一个新包，旧名留着当墓碑）。名字没定就注册 = 给自己上枷锁。
被抢注的风险对一个没人听说过的中文小说工具名本来也很低——不值得为它锁死一个还没想好的决定。

**代码上的唯一后果**：`release.yml` 是 `on: push: tags: ["v*"]` 触发的，最后一步会往 PyPI 发布，
所以**现在打任何 `v*` tag 都会红**。已经在那个文件顶上写了注释说明这是有意的。
在名字定下来之前，要发版就走 GitHub Release 附 wheel，别打 tag。

它也**没有堵住任何东西**：`uvx novel-harness` 这条路本来就被另一件事堵着——
`__main__.py` 还接不上 `nh serve`，卡在上面「还没定的三个决定」里的第 1 条（作者的库默认放哪）。
