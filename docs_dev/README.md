# docs_dev —— 维护者的决策日志

> 注意用词：本仓库里**「作者」指小说作者**，也就是这个产品的用户。
> 这个文件夹是**维护者**（我）的，跟他们无关，也永远不会分发给他们——见文末「会被用户看到吗」。

这里放**我自己**平时做决策留下的 md。和 [`docs/`](../docs/) 的区别：

| | `docs/` | `docs_dev/`（这里） |
|---|---|---|
| 写给谁 | 工程约束，AI 和贡献者都要遵守 | **我自己看的**，记当时怎么想 |
| 权威性 | 是。冲突以 ARCHITECTURE.md 为准 | **不是。** 只是思考过程 |
| AI 会读吗 | 会，CLAUDE.md 明确指路 | **不会**，除非我点名 |
| 改动成本 | 动 ADR 要写清「错了修复成本是什么」 | 想写就写，写错了划掉就行 |

一句话：**这里是「我为什么这么决定」，`docs/` 是「所以代码必须这样」。**
这里的想法要变成真正的约束，得自己搬进 `docs/` 或开一份新 ADR——否则会出现两个真相源。

## 命名规范

```
YYYY-MM-DD-主题.md
```

**时间在前**，文件按名字排序就是按时间排序，一眼看得出决策顺序。
**主题用中文**，说清这次定了什么，不要写「笔记」「想法」这种查不到的词。

```
✅ 2026-07-25-给决策日志开一个独立文件夹.md
✅ 2026-07-19-ADR0007-编辑器时机松动.md
✅ 2026-08-02-真书拿到之后先跑哪三条门槛.md

❌ 想法.md               ← 三个月后你不知道这是哪次的
❌ 决策2.md              ← 排序没意义
❌ 20260725.md           ← 有时间没逻辑，还是得挨个打开找
```

本文件 `README.md` 是唯一的例外（它是说明，不是决策）。

## 写法建议

一份决策一个文件，**不要往旧文件里追加**——追加了时间戳就失真了。
内容没有硬格式，但下面四行写全了，三个月后回看不会懵：

```markdown
# 2026-07-25 给决策日志开一个独立文件夹

**决定了什么**：一句话。
**为什么**：当时在纠结的是什么、有哪些选项。
**放弃了什么**：另一条路为什么没走——这条最值钱，最容易忘。
**什么情况下要推翻它**：触发条件。写不出来说明这个决策还没想清楚。
```

最后一行是从 ADR 借来的习惯。ADR 要求每条决策写明「加回来的触发条件」，
这样半年后想改主意时，判断依据是当初立的条件，而不是当天的心情。

## 会被小说作者看到吗

不会。四条分发路径里，只有开发者那条能看到这个文件夹：

| 小说作者怎么拿到软件 | 他能看到什么 | `docs_dev/` |
|---|---|---|
| `uvx novel-harness` / `pip install` | wheel 里只有 `novel_harness/` 包 | **看不到** |
| 下载 sdist（`.tar.gz`） | `PKG-INFO` / `pyproject.toml` / `README.md` / `src/` | **看不到** |
| 以后的 GUI 安装包 / 云端部署 | 打包好的前端 + 后端二进制，没有仓库结构 | **看不到** |
| `git clone`（开发者路径） | 整个仓库 | 看得到 |

机制上靠的是 `uv_build` + src-layout：**默认只打包 `src/novel_harness/`**，没有 MANIFEST.in、
没有 `force-include`，所以 `docs/`、`docs_dev/`、`tests/` 全都不进包。
这不是我特意排除的，是**默认就在外面**——反而要小心的是以后往 wheel 里塞前端产物时
加了 `force-include`，别顺手把 `docs*/` 一起带进去。

### 云服务器那条路是另一个问题

以后正文存本地、再同步到云端，那上传的是**小说作者的正文和 DB**，跟这个仓库里的文件没有交集——
`docs_dev/` 在我的开发机上，不在他们的工作目录里，两条路径永远不会相遇。

但那件事本身要动 [ADR 0007](../docs/adr/0007-manuscript-lives-on-disk.md)：
现在的铁律是**正文的真相源在磁盘上，DB 永远不是**。加了云同步就有了第三个副本，
「哪一份是真的」必须重新定死。**真要做的时候先改 ADR 0007，别先写同步代码。**
