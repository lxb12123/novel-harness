# 总结自治与正文对齐闭环（保存最快路 + 30 分钟自治 + 通知单源）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把“总结生成/覆写”从「只有点保存一条触发路」改造成一套自治闭环：保存仍是最快路；后台每 30 分钟自主扫全书做对齐（缺章补、不对齐覆写）；正在写的那一章防抖豁免（离开才够格、回来不停队）；正文→总结方向一律自动覆写且**绝不发通知**，通知只从「作者改总结」这一侧冒出来（单源）。全文不引入任何“让 LLM 判断哪章没总结”的结构决策——那一类信息全部查数据库，LLM 只在真正把正文压缩成总结的那一刻出场。

**Architecture:** 磁盘 Markdown 仍正文真相源，章节总结仍 append-only 版本 + 显式 head、**永远只有新版**（覆写制）。正文与总结的关系以「意思不冲突」为配对判据：总结是浓缩一版、正文可多版，最新正文与最新总结意思不冲突即配对；正文变更 → 总结该被覆写。覆写动作本身由本章节已有的调度入口（保存触发 `_trigger_refresh` 与后台 `ChapterRefreshCoordinator` 的总结分支）承载，本设计只新增**时机机制**（30 分钟自治 + 当前章防抖 + 权重调度）和**通知边界**（单源化），不新造第二条总结管线。

**Tech Stack:** Python 3.12、FastAPI、Pydantic、SQLite、React 18、TypeScript、TanStack Query、Vitest、pytest（与主任务 `2026-08-17-保存验证总结抽取与别名纠错闭环任务.md` 同一套）。

## 1. 意思第一主义：总结与正文的配对模型

- **总结是浓缩，正文是原文**：表达意思不变，细节被简化、重点依旧在。版本匹配是基于**意思**的匹配，不是文字相等。
- **总结永远只有一版**（覆写制，append-only 但 head 只指最新）；正文可以有很多版。
- **判据**：最新正文与最新总结“意思不冲突” = 配对，系统不再动作。正文任何一版改动后，只有“意思是否仍与总结一致”值得核对；不一致即该覆写。
- **实现载体（已有）**：生成总结那一刻把 `source_sha256 = 当前快照 text_sha256` 刻进总结行，之后任意时刻拿当前正文指纹与刻下的指纹比对——一致=配对，不一致=总结已过时。这个指纹是给“不用 LLM 也可靠”的冲突检测当锚点的；正文侧自动覆写不做语义二次判断。

> **原理（答“为什么绑定指纹”）**：正文入库时每版都有唯一 `text_sha256`；系统基于某版正文生成总结时，把“我当时对着哪版正文”一起写进总结行。此后比“当前正文指纹 == 总结身上指纹”即得是否过期——毫秒级、零付费、绝对可靠。让 LLM 重读全文再判“是否冲突”既费钱又有记错风险，因此指纹绑定 = 一条不需要 LLM 的可靠锚。

## 2. 触发时机：两条路，没有第三条

### 2.1 保存 = 最快路（保留，不改语义）

点保存的当下，这一章立刻进刷新队列并按既有 DAG 处理（验证 → 总结 ∥ 抽取）。唯一豁免：**正在写的那一章**（见 §3 防抖）。机器版总结在覆盖完整 / 缺分支时照常走 `ensure_refresh_coverage` 幂等位掩码。

### 2.2 30 分钟自治 = 智能路（本设计新增）

后台每 30 分钟自主扫一次全书做**对齐**，不依赖任何点击：

- 用确定性查询（查 `chapter_summary_head` 等）算出每章状态：**有总结(配对) / 无总结 / 异常**；
- 把**没总结的章** 与 **总结与正文指纹不对齐的章** 两类都送进调度（不只是缺总结那类，不对齐同样要覆写归队——这是对“只补缺”的重要扩展）；
- 调度按**权重**排优先级（§4），权重决定同一轮预算里先处理谁。

### 2.3 触发后的去向

两类结果都写进**系统记录**（`summary_reconciliation_*` / notification 轨迹 / attempt 状态），并同步到 **UI**（右栏「章节总结」与新的全书总结状态视图，§5）。完成即闭环。

## 3. 当前章防抖：正写的章不动，离开才够格

- **规则**：识别「作者当前正在写/正在改的那一章」，它的总结**不生成、不覆写**。原因：它马上可能再变；且本章总结此刻用不上（总结只在写后续章时被调用，写本章绝不用本章总结——本天条已成立）。
- **现状缺口（必须先补）**：后端目前没有任何“当前章”信息。保存时传的 chapter 是“保存哪一章”，不等于“作者现在眼睛停在哪一章”（作者可能在 WPS 里改第 7 章、切去第 10 章预览再切回）。因此需要新增一个**轻量「当前章」上报端点**：前端换章 / 开书时上报「我在第 N 章」（几乎免费的心跳，不触发任何总结/付费，只记位置），并带**心跳超时**（如 2 分钟无心跳 = 人不在，解除保护）。
- **离开 → 入队**：一旦上报离开（切到别的章），旧章失去保护，顺理成章进入队列。
- **回来不停队（关键）**：离开后再回来，**不停掉已入队的任务**。防抖只挡“从未离开过、正写着的当时那一刻”，不挡已入队的后续——避免走走停停反复。

> 与旧 autopilot 的区分：被删除的旧 autopilot 是「换章 → 立刻对刚离开的章付费总结」。本设计**不是**恢复它——换章只上报位置（免费、不触发工作），付费的总结生成仍由「保存 / 30 分钟调度」决定，只多了一条「当前章豁免」。两码事。

## 4. 权重调度：近 10 章必补，越远越衰减

- 对「没总结」与「不对齐」两类章统一套同一个衰减权重。
- 写第 N 章时，往回 `Δ ≤ 10` 的章（最近历史、写作最重要的回忆上下文）**权重 1.0，必调度**——就算没总结也**优先**生成了再写（“那在这之前就得调度章节总结工具”）。
- `Δ > 10` 越远权重越低（如 `max(0, 1 - Δ/N)`，常数可配），有总结就带、没总结先不急着补（省预算）。
- 调度器按权重排序，决定同一轮预算先补谁。**这是确定性公式，不是 LLM 判断**。

## 5. 通知单源化：正文侧静默，总结侧才出声

| 情况 | 处理 | 系统通知 |
|------|------|----------|
| 正文变，总结是机器版 | 自动覆写对齐（时机 = §2 两条路之一） | ❌ 绝不通知 |
| 正文变，总结是作者手改版 | **同样自动覆写**（靠版本历史回退，作者不满意可再去改总结） | ❌ 正文侧不通知 |
| 你手动改总结，与正文冲突 | 版本化 + 核对 | ✅ 通知（**唯一来源**） |
| 总结生成异常 / 卡住 | 进异常标记（QA 队列跳过不阻塞，§6） | 🔶 通知 |

- **理由**：正文变动是常态，每次改都通知=骚扰；覆写是对齐动作，作者没看也已把意思对齐，不需要打扰。两边都通知 = 复杂化、不闭环。
- **回环**：正文自动覆写得你不满意 → 你去改总结 → 通知从「作者改总结」这一侧冒出来。通知因此**单源**：只在总结侧。
- 分界统一成一句话：**只要是「作者动作」落在总结上且与正文冲突，通知该出现；只要是「正文自动对齐」，永远安静。**

## 6. 调度器不阻塞：卡住的跳过往下

- 30 分钟调度/保存触发的队列处理**不因单条卡住而阻塞整条链路**（沿用 Task 16 dispatcher 纪律：每轮独立 claim、单个 attempt 失败只记状态不炸线程、`recover_claimable` 只捡 PENDING/过期 RUNNING、lease/fence 防多 worker 冲突）。
- 「异常总结」标记照常在系统通知里出现（§5 末行），但**不挡着后面正常章的对齐**。

## 8. 非目标（明确不做）

- **不让 LLM 判断“哪章没总结 / 哪章不对齐”**：全程查数据库（记账本），LLM 只在把正文压缩成总结那一瞬间出场。
- **不为“换章”重新引入付费后台整理**：换章只上报位置。
- **不为当前章生成/覆写总结**：正写的章永远豁免，直到离开。
- **不做语义级“意思是否一致”判断**：正文自动覆写以指纹为锚，把“意思不冲突”留给模型生成、把“该不该覆写”交给指纹 + 权重。
