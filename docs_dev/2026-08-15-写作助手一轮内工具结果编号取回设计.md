## 一、机制总结（定稿版）

### 1. 要解决的问题

模式二一轮（一次作者发言）内会走多步：每步工具结果不断追加进历史，投影装不下时
按原样剪掉旧结果。但**后面的步骤可能还需要前面查过的内容**——重查会撞
`REPEATED_CALL` 闸（同样签名重复三次即停）并多付一次执行；自动总结又贵（模型调用）、
会错（摘要会丢/会编）、会过期（存的是旧快照）。

方案一句话：**剪掉的是"常驻内容"，留下的是"编号入口"，需要时按号取回，且取回前
先证明装得下。**

### 2. 范围界定（拍板项）

- **只活一轮**：编号清单随这一轮结束即焚（同 `TurnMemo` 的生命周期），不落库、
  不跨轮持久化。
- **不做自动总结**：存的是原文不是压缩；一行描述是确定性生成的（工具名 + 关键
  参数 + 字数），零 LLM 调用。
- **不改剪枝顺序、不调预算**：剪枝照旧，只是被剪条目的"入口"升级。

### 3. 机制

#### 3.1 编号

这一轮里每次工具派发按顺序编 `#1..#N`（并发批内按 `BatchRunner` 既有顺序固定，
模型看到的编号和存储的一致）。编号只活这一轮，不承诺跨轮稳定。

#### 3.2 集中清单（不是分散占位）

被剪的工具结果消息直接消失，另在**投影末尾**（最新工具结果之后）放一个像工具
列表那样的块：

```
已收起的结果（需要时用 get_result(id) 取回）：
#3 chapter_text · 第40章 · 5,120 字 · 首句「风雪落在肩上…」
#5 character_state · 萧决 · 第40章 · 重伤、在北荒
#7 book_index · 目录 42 章 · 1,204 字
```

选集中清单而不是原地占位的理由见问答 Q8。清单由代码每步维护，**有上限**
（`RECENT_RESULT_KEEP`，建议先定 8 条）：新的进来踢最旧的，被踢的条目模型不再
知道它存在。

#### 3.3 新只读工具 `get_result(id)`

按编号返回这一轮内存里（`live`）对应的原始工具结果。它是**不同签名**，所以不撞
`REPEATED_CALL`（问答 Q13）。

可选增强：`get_result(id, max_units=N)` 部分取回——截断返回并尾部标「（已截断）」，
先例是 `previous_tail[-limit:]`。

#### 3.4 取回预检（关键规则）

`get_result(id)` **派发时**，loop 先做一次确定性计算（零 LLM 成本）：

> 把当前所有可再生内容（老工具结果、老工具调用、中间推理）**全部假设剪掉**之后，
> 还剩多少空间；拿这个空间和要取回的结果大小比。

- **装得下 → 放行**：当场按 `project()` 同一顺序剪枝腾位（老结果换占位 → 老调用
  成对删 → 中间推理），再把内容返回、追加为**最新**一条（最新 = 剪枝优先级最低，
  不会被刚腾出来的空间又挤掉）。
- **装不下 → 拒绝**（`ok=False` 那一套）：返回「#3 有 5,120 字，腾光可再生内容也
  只够 2,000 字」，附三条出路：把问题说短一点 / `max_units` 只取一部分 / 重查一个
  更小的范围。

这条规则存在的理由是问答 Q11/Q12：**失败要发生在派发时（便宜、可见、可调整），
而不是下一次投影时（钱花了、内容从没被读过）。**

#### 3.5 失效兜底

一轮内基本不过期（同一轮里作者改正文的概率极低，但不为零——项目支持并发窗口）。
取回时顺手按正文哈希验一下（复用 `STALE_MANUSCRIPT` 的判据，成本为零），变了就回
「已失效，请重查」。

### 4. 收益与代价

| 项 | 效果 |
|---|---|
| 绕开 REPEATED_CALL | 同轮反复用同一结果不撞闸 |
| 免重跑执行 | 本地查询省得少，LLM 工具（draft）省得多 |
| 省「无谓思考」 | 模型看一行描述就能决定要不要取 |
| 存储成本 | 内容本来就在内存 `live` 里，几乎零新增 |
| 代价：决定那一次 | loop 模型驱动，「要 #7」仍是一次 LLM 调用，省不掉 |
| 代价：取回重新占上下文 | 按需取回的本义，不是缺陷；预检保证装得下才取 |
| 代价：清单占一点上下文 | 有上限，为一个块付费 |

### 5. 改动点

- `agent/loop.py`：`run_turn` 维护本轮编号清单；`project()` 剪第一档时不再写原地
  占位，改在投影末尾渲染清单；`get_result` 派发前做预检（复用 `project()` 的剪枝
  逻辑，**不许另写一套**）。
- `agent/ports.py` + `agent/tools.py`：`ToolContext` 加只读结果表引用（显式一道闸，
  同 `TurnMemo` 的位置），新增 `get_result` 工具声明 + handler。
- 测试：剪后取回内容一致、取回不撞闸、一轮结束清空、并发编号稳定、预检拒绝、
  清单上限退化、取回后上下文不超过预算。

### 6. 待拍板开放项

1. 描述要不要含**首句**（对「是不是我要的那个」判断最有用，每行多占十几个字）；
2. 界面上要不要显示「它取回了 #7」（技术上零成本，产品取舍）；
3. `RECENT_RESULT_KEEP` 具体数值；
4. 清单块末尾要不要带「当前剩余可装约 X 字」（让模型在决定取不取之前就有数，
   预检是兜底，这一行是让模型自己先避开）。

### 7. 明确不做的事

- 不做跨轮持久化（理由见 Q9/Q10：内容永久在 canonical，跨轮真正值得复用的两种
  东西——稿子、作者改过的正文状态——已有 `read_draft` 和重查机制）；
- 不做自动总结（理由见 Q1：钱、错、陈三笔账，且 ADR 0019 边界五「Prune Before
  Summarize」）；
- 不改剪枝顺序、不调预算、不引入第二套剪枝实现。

## 二、设计问答记录（为什么这么定）

> 以下按讨论发生的时间顺序记录。每条先给结论，再给当时的完整推理。

### Q1 为什么是剪枝而不是总结？

**结论**：这个架构里总结是最下策，剪枝是第一选择。

排序按「**能不能重建**」：工具结果重查一次就有，而且查回来是**更新的**，所以剪掉
它没有损失；只有不可再生的东西（作者的话）才连剪都不剪。总结排最后，因为它同时背
三笔账：**钱**（生成摘要是一次模型调用，每次被剪都要付）、**错**（摘要会丢会编，
而 loop 里工具结果是写进书的**事实来源**，错摘要可能漏进稿子且长得完全正常）、
**陈**（存下来的摘要是旧快照，重查拿到的才是当前的）。

章节滚动总结是这条规则的例外，因为它面对的是**静态且重读贵**的正文——和 loop 里
可随时重查的工具结果不是一回事。

### Q2 剪枝后那个占位有什么用？（Claude 说的"标记清除"）

**结论**：有用，且是删不掉的一层结构。四个作用：

1. **保住 wire 格式**：OpenAI 兼容接口要求 assistant 的每个 `tool_calls` 必须有
   同样数量、同样 `tool_call_id` 的 `tool` 消息接住，缺一条整个请求 400。所以要么
   留壳（内容换占位），要么把 assistant + tool **成对删**，不能只删结果。
2. **防止模型把"没给"读成"没有"**：「assistant 叫了工具但后面空着」会被读成查询
   失败或内容不存在；占位明说「被清掉了」，模型不会基于一个错误的"没有"往下推理。
3. **告诉模型这个可以拿回来**：占位原话「需要就重新查一次——重新查到的还是当前
   的」同时给出重建路径和"重建即更新"两个信息。**这是剪枝敢排第一档的前提。**
4. **让剪枝的成本决策有据可依**：占位比原文还长就不换（留给第二档成对删）。

### Q3 剪枝里的"中间推理"是什么？是模型返回的推理内容吗？

**结论**：不是思维链（CoT）。它是模型返回的**可见正文**——role=ASSISTANT、有正文、
没有 tool_calls 的消息，实践上就是**前几轮助手说过的话**。

每次模型调用后，loop 只取 `result.text` 追加进历史。带工具调用的那一步，正文和
tool_calls 合成一条；不带 tool_calls 的正文就是那一轮的最后答复。本项目的 model
port 不存推理痕迹（reasoning 字段只是配置 effort/thinking 档位，推理过程不进
canonical）。它被排在剪枝第三档的理由是三个字：**能重想**——模型自己的输出，删掉
后下次照样能重新组织，重建成本为零，且不承载 wire 完整性（没有 tool_call 要配对）。

### Q4 剪枝会不会让上下文超过模型限制？

**结论**：已知窗口且配对正确——不会，装不下会在**约 1/6 窗口处先停**；窗口未知或
填错了——会，而且没有第二道硬闸。

正常路径：预算 = 地板（工具声明 + 前缀，约 5,171 字）+ `return_units`（窗口的
1/3 换算成字，再按 2 字/token 保守折算，上限 6 万字）。272k 窗口 ≈ 5 万字预算，
实际只占窗口 20–28%，离模型硬限制很远。"上下文满"满的是**项目自己的预算**，不是
模型窗口。

会超的三条路径：① 模型没登记（`max_context_tokens=None`）→ `return_units` 回落
固定 17,000 字兜底，本地小窗口模型可能 3–4 倍超窗；② 窗口被高估（注册表/快照/作者
手填错）→ 预算按错误的大窗口算；③ `capabilities.py` 那道 `prompt+request exceeds
context window` 的校验靠 `prompt_token_budget` 触发，而 agent 的 plan 构造时传 0
（[`agent/model.py`](../src/novel_harness/agent/model.py)）——**对话这一档不生效**，
只拦抽取、滚动总结那些 prompt 已知的结构化调用。作者能做的防护是设置页手填窗口
（优先级最高）。

### Q5 CONTEXT_FULL 会提醒作者什么？

**结论**：两条。对话里留下一行系统消息（迁移 012 的 notice 机制）：

> 这段对话说得太长，装不下了。开一段新的对话，或者把要问的说得短一点——**你说过
> 的话一句都没被删掉**。

以及（如果这轮剪过东西）回执卡片上补一行：

> 这段对话太长了，为了装得下，N 条早先查到的东西被收起来了（要用它会重新查一次）。
> 你说过的话一句都没删。

回执卡片不会把系统行再念一遍（`receiptSays` 见对话里有 system 就返回 null）。
`CONTEXT_FULL` 在发起模型调用**之前**停，那一轮一分钱没花。

### Q6 重查要不要调 LLM？

**结论**：要，而且是一轮新的 LLM 调用。剪枝 0 次、重查 1 次、总结 1+ 次。

系统不会自动替模型把结果拿回来——「需要就重新查一次」里的**谁来决定需要**是模型。
流程是：下一次 `complete()`（一次新的 LLM 调用）→ 模型发出同一个工具调用 → loop
派发（本地查库/读盘，不调 LLM）→ 结果贴回。所以重查 = 先付一次 LLM 调用的钱，
工具本身才便宜。这是剪枝排第一、总结排最后的成本根源。

### Q7 编号取回 vs 重查 vs 总结，怎么比？

| | 剪掉 | 重查 | 按号取回 | 总结 |
|---|---|---|---|---|
| LLM 调用 | 0 次 | 1 次（决定） | 1 次（决定） | 1+ 次（生成） |
| 拿回的是不是最新 | — | 是 | 旧快照（一轮内基本没差） | 旧 |
| 撞不撞 REPEATED_CALL | — | 同签名会撞 | 不撞 | — |
| 能不能凭描述不取就判断 | — | 不能 | 能 | — |
| 跨轮可用 | — | 可 | 不可（一轮即焚） | 可（滚动总结） |

结论：一轮内取回优于重查（省执行 + 不撞闸 + 能凭描述跳过）；跨轮重查优于取回
（更新鲜）。清单限定在一轮内，正好踩在取回占优的区域；取回时发现过期，回退重查
——两者配合，不是竞争。

### Q8 为什么选集中清单，而不是每条原地占位？

**结论**：集中清单更好，三条理由。

1. **模型扫描更省力**：分散占位要回答"我要的东西在不在手上"得翻整段历史逐行找；
   清单看一眼末尾那一块就有答案，和它看工具列表的方式一样——那是它训练成熟的模式。
   正确流程：先看清单（0 次调用）→ 命中就 get_result（1 次调用）→ 拿到原文再分析。
2. **更省 token、天然可设上限**：占位的模板开销（"结果 #N：…；需要就用
   get_result(N) 取回"）在分散方案里重复 N 次，集中方案只出现一次；且清单是一个块，
   能明确"最多留 8 条，新的踢旧的"。
3. **实现更干净**：把"剪"和"渲染清单"分成两件事，剪照旧，清单在投影末尾单独拼
   一块（和工具声明是同一类注入物——由代码放进去，不是模型来取）。

代价：丢了"当时在哪一步查的"位置信息。但模型真正需要的是"有什么可用"，不是"我
当时在干嘛"——描述里带关键参数（第40章、萧决、重伤）就够判断。

### Q9 为什么范围只限定一轮？

**结论**：跨轮复用的收益很小、代价实打实。

收益小：本地查询（目录、同框章、正文）重查几乎零成本，重查还保证最新；真正贵的
工具是 `draft_chapter`，但稿子本来就有 `read_draft` 按号取回。代价大：① 过期必须
验证（作者可能隔三个月回来）；② 入口要重新暴露（每轮塞清单或加 `list_stored()`
工具，两头都是成本）；③ 增长无上限，要设计淘汰策略。

### Q10 "一轮即焚"是不是浪费？

**结论**：不是。内容从来就永久存在（canonical 只增不改，作者界面和 resume 都读它），
一轮即焚的只是**给模型看的编号入口**。值得长期复用的两种东西（稿子、作者改过的
正文状态）已有专门机制；本地查询结果跨轮缓存省的是几毫秒磁盘读，却要背过期验证、
入口暴露、无界增长三笔账。

如果实测发现"同一章连续好几轮反复查"频率很高，折中方案是：编号清单**落库但不进
上下文**，加只读工具 `list_stored_results()`，取回时哈希验证。上不上取决于频率。

### Q11 临界场景：取回后上下文满了怎么办？

**结论**：取回预检。装不下就**拒绝**，而不是先拿回来再爆。

坏版本：模型决定取回（付一次 LLM 调用）→ 工具执行、结果追加 → 下一次投影超预算 →
能剪的已全剪光 → `CONTEXT_FULL` 停。结果**从没被模型读过**，钱白花、步白走——这是
run_turn docstring 点名的那类失败（"那条调用等于没发生"）的最尖锐形态。

好版本：派发时确定性预检，装得下才放行；装不下返回拒绝 + 大小差多少 + 三条出路
（问题说短 / `max_units` 部分取回 / 重查更小范围）。失败发生在便宜的时候（派发前），
而不是贵的时候（模型调用之后才发现）。

### Q12 预检通过后，先腾位再取回——顺序对吗？

**结论**：对。完整顺序：

1. 模型调 `get_result(#3)`（"决定"那一次 LLM 调用已付）；
2. 预检：假设把当前所有可再生内容**全部剪光**，还剩多少空间，和 #3 的大小比；
3. 装得下 → 当场按 `project()` 同一顺序剪枝腾位，再把 #3 返回、追加为最新一条；
4. 装不下 → 拒绝 + 说明差多少 + 出路。

两个实现要点：① 剪枝必须复用 `project()` 那同一份代码和顺序，不许另写一套；
② "剪"发生在给模型看的那一层，canonical 存储仍然只增不改——这也是取回能成立的
原因（内容本来就在库里）。

### Q13 为什么 get_result 不撞 REPEATED_CALL？

**结论**：那道闸的判据是「同一工具、同样的参数，字节相同」（`(name, arguments)`），
重复超过 `repeat_limit` 即停。`get_result(#7)` 是另一个工具名，签名和原来的
`chapter_text(chapter=40)` 不同，闸拦不到——模型可以安全地把步 3 的内容再拿回来用。
这是编号取回最实在的一条收益。

## 三、背景：现有机制速览（讨论前提）

- **模式二 agent loop**：`run_turn` 一轮 = 模型多次调用 + 工具派发的循环；canonical
  只增不改，每次模型调用前把 canonical 投影成「稳定前缀 + 历史」发给模型。
- **剪枝四档**（`project()`）：老 `tool_result` 内容换 `PRUNED_RESULT` 壳 → 老
  `tool_call` 成对删 → 中间推理整条删 → 作者的话**永不剪**；还装不下就
  `over_budget` → `CONTEXT_FULL`。
- **预算**：整份 payload（messages + 工具声明）按字量；默认 = 地板 + `return_units`
  （窗口 1/3 换算，上限 6 万字）。
- **`TurnMemo`**：一轮即焚的既有先例（记这一轮撞过空的名字集合），证明"一轮即焚"
  是本架构已有的形态。
- **`read_draft`**：稿子按号取回的既有先例——编号机制不是新发明。

## 四、实现记录（2026-08-15 当天，提交见 git log）

核心按上文定稿落地，三处和定稿略有出入，照实际实现为准：

## 五、对话块压缩（2026-08-15 讨论定稿，未实现）

> 上面四节解决的是**工具结果**的复用（已实现）。这一节解决的是剩下的那一样东西：
> **作者的话**——它是唯一只增不减、永不剪的内容，也是 `CONTEXT_FULL` 的唯一来源。
> 本节是讨论定稿的设计，**一行代码没写**。

### 5.1 为什么需要压缩，压什么

剪枝负责"可再生"（工具结果、中间推理、助手先前的话），压缩负责"不可再生但太占地方"
（旧对话的语义，主要是作者的话）。两者不重叠：剪枝丢掉能捡回来的，压缩折掉捡不回来的。

### 5.2 定稿机制

1. **分块**：作者的话按章（或按对话块）切块；**一块 = 一整段对话**——作者的话 +
   模型当时的回答 + 那几轮的工具往返。canonical 全量保留，界面永远可见。
2. **触发**：投影扫描时，作者的话（不可剪部分）超过预算的一定比例（阈值待定，
   设计值如 60%），把**最旧**的块压成摘要。摘要用 `sha256(该块消息)` 做幂等键
   （同滚动总结），同一块只付一次模型调用。
3. **摘要块**：一条 `system` 消息，插在稳定前缀之后、近期对话之前（背景在前、
   原文在后，保住前缀缓存）。每行是**一句话概括，不是原话**：

   ```
   【更早的对话】第 1–40 章（机器摘要，原文仍在界面里）：
   #12 · 第 39 章前 · 作者要求别写打斗
   #18 · 第 41 章前 · 作者：萧决知道他爹是守令人
   ```

4. **取回**：扩展按号取回为**整块取回**——`get_result(id)` 把那一整块对话的原文
   调回模型视野（作者的话 + 模型回答 + 工具往返都在里面）。预检照抄第四节：
   把可再生内容全剪掉还装不下就拒绝。**取回是罕见纠错通道，不是日常路径。**
5. **回执**：压缩发生时，回执告诉作者"最早一段被压成了背景摘要"——压缩不无声发生。

### 5.3 讨论中定死的几条决策（为什么这么定）

- **取回 = 空间又还回去，这是硬数学。** 摘要负责让上下文小，取回负责偶尔确认——
  两者对着干。所以取回只能是"摘要疑似漏了/错了、需要确切措辞"时的保险丝；
  取回变频繁 = 摘要质量不行，该修摘要，不是加取回。
- **作者的话取回价值比工具结果低。** 工具结果取回省的是"重跑"（一次 LLM 执行 +
  不撞 REPEATED_CALL）；作者的话取回没有任何执行成本可省，只为对质。因此
  **不为作者的话单独造一套按条取回**——编号指向整块，是"整块取回"的自然结果，
  不是刻意功能（模型的话能重想，不值得为它单独取回）。
- **单向压缩对这个项目不够。** 摘要丢一个字可能把"不许说破"变成"可以说破"，
  而且不报错；整块取回让模型和作者都能回去核对原话（作者侧靠界面，天然成立）。
- **先想清楚要不要做。** 书的状态在数据库和工具里，不在对话里；`CONTEXT_FULL`
  本来就给了退路（开新对话）。如果真书长对话里没撞到"开新对话接不上"的案例，
  选项 1（什么都不加）仍是第一优先——本设计是"要做时的定稿"，不是"现在就要做"。

### 5.4 和已实现部分的关系

```
messages: [
  {role:"system", content: 身份},          ← 前缀①
  {role:"system", content: write_rule},    ← 前缀②
  {role:"system", content: 更早对话摘要},   ← 压缩块（设计，插在此处，带 #编号）
  {role:"user", content: 近期作者原话},      ← 保持原文
  {role:"assistant", content: …},          ← 保持原文
  {role:"tool", …},
  {role:"system", content: 已收起的结果…},   ← 工具结果清单（已实现，末尾）

```
