## 一、点保存之后——流程 + 模块对照

```
点保存
  └─▶ 写入磁盘 + 存一版快照（内容去重，判过当前版）
        │   模块：importer.py::save_chapter()
        │   入口：api/app.py::save_chapter()（PUT /chapters/{chapter}/text）
        │
        └─▶ 触发后台整理（不卡住保存本身，保存立刻返回）
              │   触发点：api/app.py::_trigger_refresh()
              │   排队：chapter_refresh.py::ensure_refresh_coverage()
              │         （只排队、只判缺口，真正跑分支是下面的后台调度器）
              │   执行：api/background_runtime.py
              │
              ├─▶ 验证检查   PENDING → RUNNING → 完成/受阻/失败
              │     模块：checks/service.py::validate_snapshot()
              │     判的是：系统规则(R3：人物开口时机，checks/dead_speaks.py::check())
              │            + 你自己记录的自定义规则（checks/custom.py），两者合并成
              │            一套 all_rules 一起判，不是分两步。
              │     → 结果落在右栏「检查」
              │
              ├─▶ 章节总结   PENDING → RUNNING → 完成/受阻/失败
              │     模块：background_runtime.py::_SummaryAdapter
              │           → draft/rolling_summary.py
              │     → 喂给之后的写作提示（不是右栏哪个 tab，是 prompt 的输入）
              │
              └─▶ 事实抽取   PENDING → RUNNING → 完成/受阻/失败
                    模块：background_runtime.py::_ExtractionAdapter
                          → extract/runner.py
                    → 结果落在右栏「待确认」
```

**验证分支的两层规则，展开说**：

- 系统规则，今天只有一条——**R3「人物开口时机」**：查已经死了、或者还没登场的
  角色，出现在说话人标签位置开口。`checks/catalog.py::SYSTEM_RULES`，
  实际判定函数是 `checks/dead_speaks.py::check()`。
  （原来还有一条 R2「未来剧透」，2026-08-27 因为界面上从来没有入口能填它要读的
  字段而删了，`checks/catalog.py` 里有原话。）
- 自定义规则：你在界面里记录过的「某个词不能出现」这类规则，
  `checks/custom.py` + `checks/service.py::load_custom_rules()`。
- 两者合并：`checks/service.py::validate_snapshot()` 里
  `all_rules = (*SYSTEM_RULES, *load_custom_rules(...))`，一次判完，不分两步。

## 二、活动记录：哪些情况「不经过你批准」直接留一条日志

| 触发点 | 干了什么 | 写进哪个来源 | 模块 |
|---|---|---|---|
| 保存后台跑「抽取」分支 | 把这一章正文里的事实抠出来 | `抽取(extraction)` + `模型调用(model_call)` | `extract/runner.py` |
| 抽取完，结果够「干净」（不落进「跟现有设定冲突 / 主要角色低置信度 / 新角色」这三个例外桶） | **自动转正成官方设定（CANON）**，不用你点确认——ADR 0020 那条决策本身 | `决策(decision)`，`actor=system` | `extract/auto_canon.py::promote_clean_facts` |
| 保存后台跑「总结」分支 | 生成滚动摘要 | `模型调用(model_call)` | `draft/rolling_summary.py`（模型调用记录复用 `extract/call_audit.py::record_call`） |
| 写作助手（模式二）直接落稿 | AI 帮你写完一段直接存进正文（ADR 0021） | `模型调用(model_call)`，`actor=system` | `agent/drafting.py` |
| 聊天 / 续写这类交互调用 | 你跟写作助手对话或让它续写 | `模型调用(model_call)` | `api/chat.py` |

相对的，**需要你先点一下**的（声明人物/别名、编辑事件角色、改/撤一条自动转正的
设定、编辑事件摘要、接受/拒绝/编辑提案）不算「免审批」——那些是你自己动的手，
`actor` 记的是作者，不在这张表里。

## 三、一条活动记录条目的字段结构

列表里折叠的一行（`ActivityEntry`）：

```
id          条目本身的标识
source      来源：extraction / model_call / decision 三选一
ts          时间戳
actor       操作者：system 或作者
status      状态
title_code + params      标题（是个代码+参数，前端拼成人话，不是写死的一句话）
subtitle_code + params   副标题，同上
chapter_number            对应第几章
jump        点开/点这一行能跳到哪（目标类型、章节、事件id、提案id、边id…）
```

点开一条看详情，多出来的字段（`ActivityDetail`）：

```
rows        明细行（比如抽取跑出来的具体几条）
cost        这次花了多少钱
errors      报错信息（如果有）
payload     决策类的，审计用的详细内容
```

后端没有一张独立的「活动」表——上面这些字段是把三张表（`extraction_run` /
`model_call` / `decision_log`）折叠成一份视图现出来的，代码在
`src/novel_harness/activity.py`（读端）+ `src/novel_harness/api/activity.py`（路由）。

## 四、这个功能为什么存在（ADR 0020，「可查 + 可改」）

系统现在允许把「干净」的抽取结果自动转正成 CANON，不再要求作者先点确认——
因为 ADR 0020 查过真实数据，「等作者批准」这道关卡**从来没人走过**
（`extraction_run` 0 行、CANON 事件 0 条、pending 提案 0 条）。但「系统可能悄悄
往书里写你没同意的东西」这个风险还在，换成了两条退路：

| 怕什么 | 事前批准（旧） | 现在的做法 |
|---|---|---|
| 作者没同意 | 挡住 | 不挡了，承认是代价 |
| 作者发现不了 | 挡住 | **每一步留痕，日志页可查**——活动记录就是干这个的 |
| 作者改不掉 | 挡住 | 配了一套编辑/撤销路由 |

ADR 原话，解释了为什么「作者」那栏经常是空的：

> 作者可能一直不看日志。那时错误会静默累积。这是本 ADR 最大的赌注：赌
> 「错了能改」比「错了先拦住」更符合一个每天写 5000 字的人的实际工作方式。
