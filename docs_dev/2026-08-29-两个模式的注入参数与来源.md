# 两个模式往 prompt 里注入什么，每一格从哪来

> 2026-08-29。逐格实读自代码，不是从旧文档抄的。
> **这一份只答两个问题**：模型收到了什么、那东西是怎么拿到的。
> 「为什么这么设计」在各自的 ADR 里，「四条流怎么走」在 `模式一数据流.txt`。

## 先分清两个轴 —— 读错这一条，下面整份表都会读歪

    project.language（书的语言）  →  **模型写正文用哪种语言**
    界面语言（前端 store）        →  **作者读菜单/通知/错误用哪种语言**

**下面两张表里的 `language` 一律指前者。** 后者一个字都不进 prompt——
2026-08-27 维护者裁定它们独立（一个中文作者可能在写英文小说）。

# 模式一 · 行内续写（作者停手 400 毫秒自动发）

| # | 块 | 怎么来的 | 花钱 |
|---|---|---|---|
| 1 | 人设 + 四条规矩 + 长度 | 后端常量，按 `project.language` 选中/英文那份 | 否 |
| 2 | 【更早章节滚动总结】 | 查 `chapter_summary` → `select_rolling_summaries` 从新往旧收，按字数预算截 | 否 |
| 3 | 【上文】 | 前端切光标前那截 → **后端按额度再截一次**（不信客户端，`following_text` 是自由字符串入口） | 否 |
| 4 | ~~【在场】~~ | cast 解析成功才渲染——**前端从不传，所以今天永远没有** | —— |
| 5 | 【这一场要写】 | 后端常量 `continuation_goal(language)`，**作者和前端都改不了**（ADR 0015 D3） | 否 |
| 6 | ~~【本场设定要点】~~ | **2026-08-26 删了**，`graph_section()` 从此恒返回空串 | —— |
| 7 | 【下文】 | 前端切光标后那截 → **只在「不是最新章」时渲染**（`track.at_frontier` 判，fail-safe：算不出来也当在最前沿） | 否 |

**整条路只有一次模型调用**（把上面拼好发出去那一次）。**2–7 全是查库或纯字符串。**

## 三个参数的唯一来源

    language        proj.language        ← 不从请求体来（国际化第一批 ②：前端传不了，
                                           `DraftRequest` 上压根没这一位）
    上下文额度      product_tail_limit(模型窗口)
                    = max(800, min(窗口/2 × TAIL_CONTEXT_SHARE, 40_000))
                    TAIL_CONTEXT_SHARE = 1/6
                    ← **公式只有后端一份**；前端拿的是 `GET /api/settings` 回的那个数，
                      `tests/test_continuation_tail_limit.py` 钉着两头不许再冒出字面量
    思考档          ReasoningEffort.OFF  ← 2026-08-26 从 HIGH 改的。改之前这条路在
                                           作者自建的端点上**恒 422**（没登记的路由只给
                                           `{OFF}`，要 HIGH 当场 CapabilityError），
                                           而报的话是「模型没配好，去填地址/模型/钥匙」

## ⚠️ 算了但一个字不进 prompt 的那一样

**轨道**（`track.py`：作者跳回去改旧章时，后面哪几章跟这一段相关）。

    进 prompt          ❌ 一个字都不许
    进出参那一格        ✅
    进事后核对那一侧    ✅

理由是**信息隔离**：第 64 章的总结里可能写着第 2 章的读者还不该知道的事，
给写第 2 章的模型看等于亲手剧透。`tests/test_track_isolation.py` 扫 AST 钉住
`draft/` 一行都不许 import `track` / `summary_index` / `advisory_review`。

# 模式二 · 写作助手

## 每一轮固定带的三样

| 块 | 怎么来的 | 落不落库 |
|---|---|---|
| 人设 + 六条规矩 | 后端常量，按语言选 | **落**（建会话时写进 `PREFIX_SECTION`） |
| 作者的文风 `write_rule` | 他开会话时填的 | **落**（同上，以后每轮从库里读回） |
| 15 个工具声明 | `tool_declarations()` | **不落，每轮现算** |

⚠️ **前两样和第三样的生命周期不同**：改了工具表，**已有会话下一轮就看到新的**；
改了人设，**已有会话永远是它建立时那一份**。（2026-08-27 查证，此前我说反过。）

## 它调 `draft_chapter` 那一次，额外装的

```
ChapterDraftRequest(
    goal                = 封存简报的内容 + 一句「写完给自己一句自述」
    length              = 会话上那一档
    previous_tail       = 从磁盘读上一章末尾
    write_rule          = 会话上那条文风
    brief               = seal_scene_brief 封存的不可变产物
    target_chapter_text = 目标章当前正文（重写老章时才有）
)
```

## 那次调用的记忆前言 —— **整章起草才有，续写没有**

| 块 | 取数 | 预算 |
|---|---|---|
| 【近八章事件】 | 已确认事件，按章距 | **4/7** |
| 【更早的相关事件】 | 同上，更远的 | **1/7** |
| 【更早章节滚动总结】 | 同模式一 | **2/7** |
| 【在场人物资料】 | 抽取写的画像（性别 / 性格 / 背景 / 备注） | 跟着上面切 |

**预算总量** = `(窗口余量 / TOKENS_PER_UNIT) × MEMORY_CONTEXT_SHARE`
（`TOKENS_PER_UNIT = 2`、`MEMORY_CONTEXT_SHARE = 1/3`），上限 60,000 字。

# 两个模式最要紧的三处差别

**① 记忆前言：模式二四块，模式一只有滚动总结一块。**

理由写在 `product_context.py` 的注释里：**续写整个预算是 400 毫秒**，
总结那一格是纯查库（不额外花钱），事件和画像要查图要算，塞不进那条路。

**② `goal` 的来源完全不同。**

    模式一   后端常量，作者和模型都改不了
    模式二   封存简报，模型自己 calibrate_scene + seal_scene_brief 出来的

**③ 语言：两个模式都跟 `project.language`。**
作者读的那一侧（界面/通知/错误）跟的是**界面语言**，两个轴不许合并。
